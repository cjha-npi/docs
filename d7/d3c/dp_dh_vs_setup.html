VS Setup

This page describes Visual Studio IDE settings that should be configured for a consistent development environment. These settings affect the editor, formatting behavior, extensions, UI preferences, debugging experience, and other user-level Visual Studio behavior.

Browsing Database Location

The folder location used for browsing database and IntelliSense files. This folder can become very large, often several GB. By default, Visual Studio stores these files in the .vs folder inside the solution folder, which can make the solution folder unnecessarily large and make cleanup tedious. To avoid this, use a separate cache location outside the solution folder. The preferred folder name is VS_Caches.

  • VS 2022: Tools > Options... > Text Editor > C/C++ > Advanced > Browsing Database Fallback
    • Always Use Fallback Location: True
    • Do Not Warn If Fallback Location Used: True
    • Fallback Location: F:\Misc\VS_Caches
  • VS 2026: Tools > Options... > Languages > C/C++ > Intellisense > Browsing & navigation > Location
    • Always use the specified custom location for the browsing database: Enabled
    • Custom location for browsing database files: F:\Misc\VS_Caches
Note
  • The option can be found by searching for browsing database in the Tools > Options... window.
  • The option Do Not Warn If Fallback Location Used is not available in VS 2026. Instead, when the custom location is used for the first time, a popup appears with a Do not prompt again checkbox. Enable this checkbox to prevent the popup from appearing again. The same popup is also available in VS 2022.
Warning
Visual Studio expects the parent folder of VS_Caches to exist. For example, if the cache location is F:\Misc\VS_Caches, then F:\Misc must already exist. Visual Studio can recreate the VS_Caches folder itself, but it does not create the missing parent folder. If the parent folder is missing, the browsing database and IntelliSense may stop working.

Copy Project Code on Save

The Copy_Proj_Code_On_Save Visual Commander extension automatically creates a filtered backup of the Visual Studio project containing a document whenever that document is saved. Visual Studio determines the directory containing the project's .vcxproj file and passes that directory to:

D:\ToolBox\CopyProjCode\CopyProjCode.cmd

The script mirrors the whitelisted project files from F: to the corresponding path under E: while preserving the complete directory structure. For example:

F:\Eval\Group\DataSync

is copied to:

E:\Eval\Group\DataSync

Only manually created project files matching the following whitelist are copied:

*.h
*.hpp
*.c
*.cpp
*.ui
*.qrc
*.md
*.png
*.ico

Generated files, Visual Studio project files, hidden files and directories, and directories such as x64, x86, bin, obj, out, and build are excluded. Directories containing no whitelisted files are not retained in the destination.

Robocopy copies only new or changed files and removes destination files that no longer exist in the source project. The destination files are temporarily made writable during the copy operation and marked as read-only afterward to reduce the risk of accidental modification.

Copy results are appended to:

D:\ToolBox\CopyProjCode\CopyProjCode.log

Robocopy result codes below 8 indicate successful or informational outcomes, while result codes of 8 or higher indicate a failure.

Installation

Save the following script as D:\ToolBox\CopyProjCode\CopyProjCode.cmd:

@echo off
setlocal EnableExtensions DisableDelayedExpansion
set "sourceRoot=F:\"
set "destinationRoot=E:\"
set "source=%~f1"
if not defined source exit /b 2
if not exist "%source%\" exit /b 3
if /I not "%source:~0,3%"=="%sourceRoot%" exit /b 0
if /I "%source%"=="%sourceRoot%" exit /b 4
rem Preserve the complete path below F:\.
rem F:\A\B\C\SomeProj becomes E:\A\B\C\SomeProj.
set "destination=%destinationRoot%%source:~3%"
set "logDir=D:\ToolBox\CopyProjCode"
set "logFile=%logDir%\CopyProjCode.log"
if not exist "%logDir%\" md "%logDir%" >nul 2>&1
rem Allow Robocopy to update and delete existing backup files.
if exist "%destination%\" (
attrib -R "%destination%\*" /S >nul 2>&1
)
robocopy "%source%" "%destination%" ^
*.h *.hpp *.c *.cpp *.ui *.qrc *.md *.png *.ico ^
/S /PURGE /R:1 /W:1 /XJ ^
/XD ".*" "x64" "x86" "bin" "obj" "out" "build" ^
/XF ".*" "*.sln" "*.vcxproj" "*.vcxproj.filters" "*.vcxproj.user" ^
/NFL /NDL /NJH /NJS /NP >nul
set "result=%errorlevel%"
rem Remove directories that became empty after filtering or deletion.
if exist "%destination%\" (
for /F "delims=" %%D in (
'dir "%destination%" /AD /B /S 2^>nul ^| sort /R'
) do rd "%%D" 2>nul
rd "%destination%" 2>nul
)
rem Protect all copied backup files from accidental modification.
if exist "%destination%\" (
attrib +R "%destination%\*" /S >nul 2>&1
)
>>"%logFile%" echo [%date% %time%] Result %result%: "%source%" to "%destination%"
rem Robocopy return codes below 8 are successful or informational.
if %result% GEQ 8 exit /b %result%
exit /b 0

Install the Visual Commander extension by Sergey Vlasov in Visual Studio. Then open Extensions > VCmd > Extensions..., click Add, and create an extension named Copy_Proj_Code_On_Save using the C# v4.0 language. Paste the following code:

public class E : VisualCommanderExt.IExtension
{
public void SetSite(
EnvDTE80.DTE2 DTE,
Microsoft.VisualStudio.Shell.Package package)
{
events = DTE.Events;
documentEvents = events.DocumentEvents;
documentEvents.DocumentSaved += OnDocumentSaved;
}
public void Close()
{
if(documentEvents != null)
documentEvents.DocumentSaved -= OnDocumentSaved;
}
private void OnDocumentSaved(EnvDTE.Document document)
{
try {
EnvDTE.ProjectItem projectItem = document.ProjectItem;
if(projectItem == null)
return;
EnvDTE.Project project = projectItem.ContainingProject;
if(project == null || string.IsNullOrEmpty(project.FullName))
return;
string projectDir =
System.IO.Path.GetDirectoryName(project.FullName);
if(string.IsNullOrEmpty(projectDir))
return;
projectDir = System.IO.Path
.GetFullPath(projectDir)
.TrimEnd('\\');
if(!projectDir.StartsWith(
sourceRoot,
System.StringComparison.OrdinalIgnoreCase))
return;
string commandProcessor =
System.Environment.GetEnvironmentVariable("ComSpec");
if(string.IsNullOrEmpty(commandProcessor))
commandProcessor = "cmd.exe";
System.Diagnostics.ProcessStartInfo startInfo =
new System.Diagnostics.ProcessStartInfo();
startInfo.FileName = commandProcessor;
startInfo.Arguments =
"/d /c \"\"" + scriptPath + "\" \"" + projectDir + "\"\"";
startInfo.UseShellExecute = false;
startInfo.CreateNoWindow = true;
startInfo.WindowStyle =
System.Diagnostics.ProcessWindowStyle.Hidden;
System.Diagnostics.Process process =
System.Diagnostics.Process.Start(startInfo);
if(process != null)
process.Dispose();
}
catch(System.Exception) {
// Ignore failures to avoid disrupting document saves.
}
}
private const string sourceRoot = @"F:\";
private const string scriptPath =
@"D:\ToolBox\CopyProjCode\CopyProjCode.cmd";
private EnvDTE.Events events;
private EnvDTE.DocumentEvents documentEvents;
}

Click Save, then click Compile. Verify that Compilation status shows Success, and then click Install. Restart Visual Studio if necessary.

BUG: Sophos DLL

BUG
std::system_error due to Sophos Endpoint Agent

The Sophos Endpoint Agent may inject SophosED.dll into a process started under the Visual Studio debugger. In the observed case, SophosED.dll throws and catches std::system_error internally. Visual Studio reports this as a first-chance exception, so the Debug Output window may show messages similar to this:

Exception thrown at 0x00007FFFB5691B6A in <project name>.exe: Microsoft C++ exception: std::system_error at memory location 0x000000F4F98FE950.
Exception thrown at 0x00007FFFB5691B6A in <project name>.exe: Microsoft C++ exception: std::system_error at memory location 0x000000F4F98FEA80.
Exception thrown at 0x00007FFFB5691B6A in <project name>.exe: Microsoft C++ exception: std::system_error at memory location 0x000000F4F98FE9F0.

This was observed three times during startup. If the application continues normally, there is no Unhandled exception, and the process exits with code 0, this is debugger noise and can be ignored.

The messages can be hidden from the Visual Studio Output window, but doing so hides all exception messages in that window. A better fix is to add a narrow Sophos exclusion for the affected development/debug output folder, if that is allowed by the system administrator.
