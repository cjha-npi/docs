Overview

Introduction

This page describes a custom Doxygen output generation setup. The main purpose of this setup is to make the generated documentation easier to navigate, easier to inspect, and better suited for large C++/Qt projects.

The generated documentation is based on standard Doxygen HTML output, but it is extended with:

  • JavaScript
  • CSS
  • Header and footer HTML template modifications
  • Supporting external assets

The customization focuses on practical improvements such as:

  • improved navigation
  • custom page organization
  • integration of project-specific documentation pages
  • persistent project-specific browser storage
  • additional debug and inspection helpers
  • custom styling

The custom doxy-plus.js and doxy-plus.css files add an additional enhancement layer on top of Doxygen's generated pages without changing the documented source code itself.

Generation Flow

The documentation output is generated in multiple stages. Doxygen first reads the project source files, Markdown pages, configuration options, and custom HTML templates. It then generates the standard HTML documentation output. After the standard Doxygen output is generated, the custom Doxy-Plus layer extends the generated pages through additional JavaScript, CSS, header template changes, footer template changes, and supporting external assets.

The general flow is:

  • Doxygen reads the project configuration from the Doxyfile.
  • Doxygen processes the source files and Markdown documentation pages.
  • Doxygen generates the default HTML output.
  • The custom header and footer templates inject additional HTML, CSS, and JavaScript.
  • doxy-plus.js enhances navigation, browser storage, page behavior, and debug helpers.
  • doxy-plus.css modifies the layout and visual presentation.

Main Files

The custom Doxygen output generation setup is built from several files, each file has a specific responsibility in the final generated documentation.

Runtime Behavior

After a generated HTML page is opened in the browser, the standard Doxygen page is loaded first. The custom Doxy-Plus layer then runs on top of the generated page and applies additional behavior without modifying the documented source code itself.

The runtime behavior mainly includes:

  • reading Doxygen-generated page data
  • building enhanced navigation data
  • initializing the custom navigation panes
  • detecting page-local anchors and hash targets
  • restoring stored page and layout state
  • applying project-specific browser storage
  • adjusting layout-related CSS variables
  • improving search box behavior
  • exposing debug and inspection helpers through the browser console

Most runtime behavior is handled by doxy-plus.js. Styling and layout changes are handled by doxy-plus.css, while the custom header and footer HTML provide the required page structure, metadata, and script/style references.

Navigation Enhancements

The custom Doxy-Plus layer improves the navigation structure of the generated documentation. Standard Doxygen navigation is preserved, but additional navigation data and layout behavior are added on top of it to make large documentation outputs easier to browse.

The navigation enhancements mainly focus on:

  • Root Navigation
  • Page Navigation
  • Persistent Navigation State
  • Responsive Behavior

Root Navigation

The root navigation provides a high-level view of the generated documentation. It is built from Doxygen-generated navigation data and reorganized into a cleaner structure for browsing important documentation areas.

Typical root navigation entries include:

  • overview pages
  • namespaces
  • classes
  • concepts
  • files
  • examples
  • dependencies
  • architecture/design pages
  • code file pages
  • development hub pages

The purpose of the root navigation is to provide a stable top-level structure that is easier to browse than the default generated navigation tree.

Page Navigation

The page navigation provides quick access to important sections inside the currently opened page. It is based on page-local headings, anchors, and hash targets.

This helps with:

  • jumping to a specific section
  • restoring the previously selected section
  • highlighting the current navigation item
  • expanding the required navigation branch
  • keeping pagenavigation synchronized with URL

Persistent Navigation State

Some navigation-related settings can be stored in project-specific browser storage. This allows the generated documentation to remember selected layout and navigation behavior between page loads.

Examples include:

  • previous page
  • previous hash
  • root pane width
  • leaf pane width
  • generated root and page navigation data
  • vertical scroll position

Responsive Behavior

The navigation layout can change depending on the available screen width. This prevents the custom navigation panes from taking too much space on smaller screens while keeping the enhanced layout available on larger screens.

The final behavior is controlled by the custom JavaScript, custom CSS, browser storage, and the generated Doxygen page structure.

Browser Storage

The custom Doxy-Plus layer uses browser storage to preserve generated data, navigation state, and user layout preferences between page loads. This reduces repeated processing and allows the generated documentation to keep a consistent browsing state.

The stored data is kept project-specific so that multiple documentation outputs on the same origin do not overwrite each other's data.

The browser storage is mainly used for:

  • generated root navigation data
  • generated page navigation data
  • previous page and hash state
  • navigation pane widths
  • navigation visibility options
  • cached generation metadata
  • expiry information for stored data

Stored Navigation Data

Some generated navigation data can be stored after it is built. This allows the documentation to reuse the processed structure instead of rebuilding it from scratch on every page load.

Typical stored navigation data includes:

  • root navigation data
  • page navigation data
  • ignored or skipped navigation entries
  • generated metadata used to validate cached data

Stored Page State

The browser can store the previously opened page and the previously selected hash target. This makes it possible to restore useful navigation context when the documentation is opened again.

Typical stored page state includes:

  • previous HTML page
  • previous hash target
  • current-page vertical scroll position
  • expanded or visible navigation areas

Stored Layout Options

Some layout settings can be stored so that the documentation keeps the user's preferred view between page loads.

Typical stored layout options include:

  • root navigation pane width
  • leaf navigation pane width
  • dual-pane navigation state
  • page navigation visibility
  • automatic list hiding behavior

Expiry Handling

Stored data can become stale when the documentation is regenerated or when the Doxygen configuration changes. For that reason, cached data should be validated and expired when needed.

The storage layer can use expiry metadata to remove old entries and avoid using outdated navigation or page data.

Clearing Stored Data

If the generated documentation behaves incorrectly after a major documentation update, clearing the stored browser data can help. This is especially useful when old cached navigation data no longer matches the newly generated HTML output.

Dox Extension Setup

A Doxygen configuration file does not need to be named Doxyfile. Doxygen only cares about the file contents, not the file name or extension. For convenience, the configuration file can therefore be saved with a .dox extension and associated with Doxygen on Windows.

After the .dox extension association is configured:

  • Double-clicking a .dox file will run Doxygen using that file
  • Command Prompt window will automatically open and show details
  • Command Prompt window will automatically close after documentation generation is complete

This makes it extremely easy to run Doxygen generation. Below are the ways to configure, check and remove the .dox extension association on Windows.

Create Dox Extension Association

Keep the Doxygen configuration file contents unchanged, but save the file with a .dox extension. Then open Command Prompt as Administrator and run:

assoc .dox=Doxygen.Config

This associates all .dox files with the custom Doxygen.Config file type.

Configure Dox Extension Execution

In the Administrator level Command Prompt, if doxygen.exe is available through the PATH environment variable, then use:

ftype Doxygen.Config="%SystemRoot%\System32\cmd.exe" /d /c "for %%I in (%1) do pushd ""%%~dpI"" && doxygen ""%%~nxI"""

Else, if doxygen.exe is not available through PATH, use the full executable path instead. For example, if Doxygen is installed here C:\Program Files\doxygen\bin\doxygen.exe then use

ftype Doxygen.Config="%SystemRoot%\System32\cmd.exe" /d /c "for %%I in (%1) do pushd ""%%~dpI"" && C:\Progra~1\doxygen\bin\doxygen.exe ""%%~nxI"""

Check Dox Extension Association

To verify the .dox association, in an Administrator level Command Prompt, run:

assoc .dox
ftype Doxygen.Config

Remove Dox Extension Association

To revert the association, in an Administrator level Command Prompt, run:

assoc .dox=
ftype Doxygen.Config=

Bugs and Fixes

Broken Hash with INLINE_SIMPLE_STRUCTS

BUG
Doxygen Overview: Broken Hash with INLINE_SIMPLE_STRUCTS

In Doxyfile, the INLINE_SIMPLE_STRUCTS tag can be used to make simple POD-like structs appear inside the documentation of their parent file, namespace, group, class, or struct instead of being generated as separate documentation pages.

According to Doxygen:

When the INLINE_SIMPLE_STRUCTS tag is set to YES, structs, classes, and unions with only public data fields or simple typedef fields will be shown inline in the documentation of the scope in which they are defined (i.e. file, namespace, or group documentation), provided this scope is documented. If set to NO, structs, classes, and unions are shown on a separate page (for HTML and Man pages) or section (for LaTeX and RTF). The default value is: NO.

Doxygen generates HTML pathname for each struct, these HTML pathname contains forward slashes i.e. / (if CREATE_SUBDIRS = YES) and other characters that are valid HTML pathnames but not valid in a raw CSS id selector. When INLINE_SIMPLE_STRUCTS = YES, Doxygen uses the exact same HTML pathname as hash links, this causes jQuery/Sizzle to throw errors such as:

Syntax error, unrecognized expression: #d5/d42/...

The exception aborts the click handler and can break navigation, highlighting, and page-nav logic.

Associated GitHub Bug Report: Incorrect links in case of use INLINE_SIMPLE_STRUCTS (GitHub issue **#8596**)

To work around this broken hash-link problem, a patch has been implemented in doxy-plus.js, this patch has to be implemented at the top of the outermost IIFE:

; (function ($) {
'use strict';
// Patch jQuery to not throw when "#id" fragments contain CSS-invalid characters such as '/'.
(function () {
// Purpose
// Patch jQuery so that simple "#id" selectors created from Doxygen hash fragments do not throw.
// Doxygen (notably navtree.js) sometimes does $(hash) where hash comes from a link fragment.
// With some settings (e.g. INLINE_SIMPLE_STRUCTS=YES in doxyfile), those fragments can contain
// '/' and other characters that are not valid in a raw CSS id selector. jQuery/Sizzle then throws:
// "Syntax error, unrecognized expression: #d5/d42/..."
// The exception aborts the click handler and can break navigation/highlighting/page-nav logic.
//
// What this patch changes
// It monkey-patches jQuery's internal constructor $.fn.init (used by $()/jQuery()).
// For selectors that are a very simple "#something" (not complex CSS expressions), it escapes
// the id portion so that characters like '/' become '\/'. This makes the selector valid CSS,
// so jQuery returns an empty set instead of throwing.
//
// Scope and safety
// The patch is intentionally narrow:
// - Only touches selector strings that look like a simple "#id" (no spaces, combinators,
// attribute selectors, pseudo selectors, selector lists, etc.).
// - Does not change complex selectors to avoid altering legitimate query semantics.
// - Uses jQuery.escapeSelector when available (jQuery 3+), otherwise uses a conservative
// fallback escaping rule.
//
// Load order
// This code installs immediately if jQuery is already present. If not, it retries briefly
// using setInterval until jQuery loads, then patches once and stops retrying.
//
// Behavioral impact
// - Eliminates the "unrecognized expression" console errors for invalid hash-based selectors.
// - Prevents exceptions inside Doxygen handlers, allowing navigation logic to continue.
// - If the escaped id does not exist in the DOM, jQuery returns an empty set (normal behavior).
function escapeIdSelector(id) {
// Prefer jQuery's official escaper when present (jQuery 3+).
if (window.jQuery && typeof window.jQuery.escapeSelector === "function") {
return window.jQuery.escapeSelector(id);
}
// Fallback: escape anything that is not [A-Za-z0-9_-]
return String(id).replace(/[^a-zA-Z0-9_-]/g, function (ch) { return "\\" + ch; });
}
function patchOnce() {
var $ = window.jQuery;
if (!$ || !$.fn || !$.fn.init) return false;
if ($.fn.init.__doxyPlusPatched) return true;
var origInit = $.fn.init;
function isSimpleIdSelector(s) {
// Only rewrite very simple "#something" selectors.
// Do NOT touch complex selectors (spaces, combinators, attrs, pseudos, commas).
return typeof s === "string" &&
s.length >= 2 &&
s.charAt(0) === "#" &&
s.indexOf(" ") === -1 &&
s.indexOf(">") === -1 &&
s.indexOf("+") === -1 &&
s.indexOf("~") === -1 &&
s.indexOf(",") === -1 &&
s.indexOf("[") === -1 &&
s.indexOf(":") === -1;
}
var patchedInit = function (selector, context, root) {
if (isSimpleIdSelector(selector)) {
var rawId = selector.slice(1);
selector = "#" + escapeIdSelector(rawId);
}
return origInit.call(this, selector, context, root);
};
patchedInit.prototype = origInit.prototype;
patchedInit.__doxyPlusPatched = true;
$.fn.init = patchedInit;
return true;
}
// Install ASAP, even if our file loads before jquery.js.
if (patchOnce()) return;
var t = setInterval(function () { if (patchOnce()) clearInterval(t); }, 10);
})();
// ... Rest of the code
})(jQuery);
