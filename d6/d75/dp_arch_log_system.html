Log System

Introduction

The logging system replaces Qt's default message handler and provides asynchronous file logging, optional console or debugger display, important-log forwarding, runtime configuration, persistent settings, directory cleanup, and best-effort fatal and crash reporting. Normal messages are written to a process-specific *.log file. Crash, fatal and late messages are forwarded to a separate helper process that maintains a corresponding *.imp.log file. Critical messages, and warning messages when configured as important, are also forwarded to the helper while remaining available in the normal *.log file.

Reference Project: D146_Log_Gui

Final Evaluation Project: E131_GUI

Details

Log.h provides the Public Interface for querying and changing logging settings, controlling display output and enabling testing features.

Log.cpp contains the Windows-specific implementation. The main components are:

  • Message handler: Captures messages, sequence numbers, timing and context information, then routes the records for output.
  • Context caches: Store category, file/line and function text so queued records can use compact indices instead of repeatedly processing the same text.
  • Workers: Format and write normal logs, forward important warnings and handle console/debugger display.
  • Important-log bridge: Sends important records to the separate npiImpLog.exe helper process.
  • Configuration: Validates settings, manages persistent storage, switches directories and schedules cleanup.
  • Fatal and crash handling: Performs best-effort reporting without relying on the normal worker queues.
  • Testing: Provides optional message-handler timing.

Normal Message Flow

Qt logging call
-> Message handler
-> File queue
-> File worker
-> Normal .log file
-> Display queue, when enabled
-> Display worker
-> Console or debugger

The file worker is the only producer of the display queue. Critical messages are also sent directly to the important-log helper, while configured important warnings are forwarded by the file worker. Fatal, crash and late messages use separate paths rather than the normal queues.

Note
The central logging state remains alive until process termination so logging can continue during shutdown and static destruction.

Initialization and Shutdown

Initialization

The logging system initializes automatically before main() through Q_CONSTRUCTOR_FUNCTION. Application code does not call its private initialization functions.

Initialization performs the following work:

  1. Installs crash handlers, the Qt message handler and the logging-category filter.
  2. Loads persistent settings and applies category rules and output fields.
  3. Schedules directory cleanup, starts the important-log helper and file worker, and starts the display worker when a console or debugger is available.
  4. Registers normal process shutdown through std::atexit.
Note
Normal logging does not require a QApplication instance or a call to QCoreApplication::processEvents() for initialization.

Shutdown

When the application emits aboutToQuit, any pending folder-size setting is saved and optional message-handler timing is stopped.

At normal process exit, the registered shutdown callback:

  1. Enables shutdown mode.
  2. Stops and joins the file worker.
  3. Stops the display worker after the file worker has finished forwarding records.

Messages received after shutdown mode is enabled bypass the normal queues and go directly to the important-log helper and, when attached, the debugger.

If console output is blocked, for example by selected text, the user can choose to continue waiting or finish shutting down without waiting for the display worker.

Warning
Fatal errors and crashes do not follow normal shutdown. Normal logs still waiting in the queues may remain unwritten.

Log Output

Normal files, important files and display output serve different purposes. Display settings do not change which records are written to files.

Log files and naming

A new file base name is generated during startup and when a different log directory is selected.

yyyyMMdd_HHmmsszzz_PXXXXXXXX

The date and time are local. XXXXXXXX is the process ID as eight uppercase hexadecimal digits.

  • Normal file: <base-name>.log
  • Important file: <base-name>.imp.log

Active log files can be read by other programs, but cannot be moved or deleted while open. A directory change closes the previous files and starts new files in the selected directory.

Note
The important file is created only when the helper receives its first important record. Its absence normally means no important record has been written.
Important logs

npiImpLog.exe receives records through a pipe and writes them independently of the application's normal file worker.

  • Warnings: Forwarded by the file worker when warning-as-important is enabled.
  • Critical messages: Sent directly from the message handler and also queued for normal logging.
  • Fatal and crash records: Sent through the emergency reporting paths.
  • Late messages: Sent directly after shutdown mode is enabled and marked [LATE].

The primary important file is in the active log directory. If the helper cannot open or create it, it tries the same file name inside the application's program-data ImpLogs directory.

Note
The backup location is a fallback, not a second copy of every important log.

The message is always appended after the selected fields, separated by | . Important records use a fixed layout containing all fields.

AppTime and ThreadTime use hhh:mm:ss.zzz, where zzz is milliseconds. ThreadDelta uses an adaptive unit: u for microseconds, z for milliseconds, s for seconds, m for minutes and h for hours. The first message from a thread uses [INIT].

Note
  • Field names are case-insensitive. Invalid names and duplicates are ignored.
  • If no valid field remains, the corresponding default layout is used.
  • File and function information depend on the message context available in the build.
  • Sequence numbers can wrap, and elapsed-time fields stop increasing at 999:59:59.999.
Text sanitization and limits

Formatted records use ASCII text and occupy one physical line.

  • Leading whitespace is removed.
  • Repeated whitespace, including tabs and newlines, is collapsed into a space.
  • Supplied | characters become / because | is reserved for field separation.
  • Unsupported characters become ?.
  • Fixed formatting buffers mean oversized records may be truncated.

Context caches and their text pools also have fixed capacities. When context text is unavailable or cannot be cached, the corresponding field uses ?.

Console and debugger display

The display worker prefers an attached console. Otherwise, it uses debugger output when a debugger is attached. Without either target, normal and important file logging continue without display output.

  • A console attached during startup is treated as permanent.
  • A temporary console can be opened and closed through the public interface.
  • Console colors depend on the message level; debugger output is uncolored.
  • Warning, information and debug display can be controlled separately.
  • Display muting is runtime-only.

Debug and information messages are subject to a display rate limit of 4096 lines per second. Suppressed output is reported with a summary. Warning and critical messages are not suppressed by this rate limit.

Display forwarding also has a queue-backlog limit. Under heavy load, forwarding may be skipped and a warning is recorded in the normal log.

Note
Display suppression does not remove records from the normal file.
Fatal and crash reporting

Fatal messages bypass the normal queues, attempt important-log and debugger output, display an external popup and terminate the application.

For concurrent fatal messages, only the first thread to claim fatal ownership performs the reporting. Other fatal threads allow it a short grace period before forcing termination. A repeated fatal message on the owning thread forces termination without waiting on itself.

Crash handlers use restricted, best-effort reporting and do not rely on the normal workers.

Warning
  • Complete reporting cannot be guaranteed after process corruption or output failure.
  • Synchronous pipe writes can still block.
  • Normal records waiting in the queues may remain unwritten.

Temporary mode

Temporary mode prevents subsequent configuration changes from being saved. Runtime changes still take effect.

Disabling temporary mode does not automatically save or revert those changes. Reapplying a setting with temporary mode disabled can save its current value.

Note
Enabling temporary mode does not cancel a folder-size save that was already scheduled.
Category rules

Built-in category rules depend on the build configuration. Custom rules are applied after the built-in rules and can override them.

  • Debug messages in npi categories are disabled by default.
  • Information messages in npi categories are enabled by default.
  • Whitespace is removed from custom rules.
  • Rules require a non-empty key, exactly one =, and a true or false value.
  • Invalid rules are discarded.
  • addFilterRule() appends a rule; setFilterRules() replaces the complete custom list.
  • Removing custom rules leaves the built-in rules active.

Use baseFilterRules() to inspect the current build's built-in rules.

Directory validation and switching

Directory paths are trimmed, normalized, created if needed and checked for write access before use. Accepted paths must be drive-letter absolute paths, including mapped drives. Empty, relative, drive-relative and UNC paths are rejected.

A successful directory change:

  1. Starts an important-log helper for the new directory.
  2. Switches the file worker and waits until the new normal file is ready.
  3. Updates the active directory and file base name, schedules cleanup and saves the directory when temporary mode is disabled.

Directory changes are serialized so these operations do not overlap.

Selecting the current directory again does not switch files, but can still save the directory setting. resetDirectory() uses the same validation and switching path to restore the default.

Warning
Rejected paths leave the current directory active. Failures establishing required output during a directory switch are treated as fatal.
Folder cleanup

The configured size is a cleanup target for managed normal log files, not a continuously enforced quota. A value of 0 disables size-based cleanup.

Cleanup runs asynchronously:

  • During startup.
  • After a successful directory change.
  • After a folder-size change has settled.

Only normal log files matching the system's naming format are counted. Important logs, unrelated files and symbolic links are excluded. Older files are removed first until the target is reached or no more files can be removed.

Cross-process locking prevents overlapping cleanup operations. New requests cause older cleanup operations to stop when they detect that they are outdated.

Folder-size changes update the runtime value immediately. Cleanup and persistent saving use separate 2.5-second debounce timers to avoid repeated work during rapid changes. A pending save is completed when the application emits aboutToQuit.

Note
  • Files still open by an application cannot be deleted, so cleanup may not reach its target.
  • Logs can grow beyond the target between cleanup operations.
  • Important logs require separate retention or removal by the application or user.

Maintenance

Keep Log.h, Log.cpp, this page and the helper executables consistent when making changes.

  • Public interface: Update function documentation and usage examples when changing behavior, parameters or return values.
  • Fields: Update field names, layout packing, formatting and default layouts together. Keep field values compatible with the four-bit packing scheme and review the fixed important-log layout.
  • Settings: Keep defaults, validation, saving and reset behavior consistent. Check how existing settings files behave after a change.
  • Helpers: Keep helper paths, arguments and pipe communication compatible. Deploy updated helper executables when their behavior changes.
  • Workers: Preserve queue ownership and shutdown order. The file worker produces display records and must stop before the display worker.
  • Shared state: Preserve synchronization, completed cache-entry publication and the process-lifetime state needed during shutdown.
  • Fatal and crash handling: Keep emergency reporting independent of normal workers. Avoid introducing recursive logging or unnecessary allocations in these paths.
  • Timing: Keep timing reports outside Qt logging and preserve consistent time/count snapshots.

Repeat the relevant checks in Testing after implementation changes or Qt/toolchain updates. Update the recorded environment, results and any tests not repeated.

Log context cache

This test was performed to check whether the caches responsible for storing text from different parts of QMessageLogContext behave correctly.

The logging system uses three different caches:

  1. CategoryCache: Stores the log category.
  2. FileLineCache: Stores the file and line information.
  3. FunctionCache: Stores the function information.

All three caches generate text from data provided by QMessageLogContext. The context contains raw pointers to the file, function, and category texts, along with an integer line number. Each cache generates a hash from the referenced text, converts it into an index for reuse, and stores the normalized text in a pool. The test was performed to verify that the caches generate the correct indices and store the correct text.

Relevant test code:

// slot connected to a QPushButton
void MainWindow::on_logCtxCheck_btn_clicked()
{
static int counter{0};
++counter;
static std::array<char, 128> fileBuf{};
static std::array<char, 128> funcBuf{};
static std::array<char, 128> cateBuf{};
std::snprintf(fileBuf.data(), fileBuf.size(), "some/file_%d.cpp", counter);
std::snprintf(funcBuf.data(), funcBuf.size(), "void func_%d()", counter);
std::snprintf(cateBuf.data(), cateBuf.size(), "npi.temp_%d_cat", counter);
QMessageLogger(fileBuf.data(), 11, funcBuf.data(), cateBuf.data()).info()
<< QStringLiteral("Testing Context with Counter: %1").arg(counter);
}

The fileBuf, funcBuf, and cateBuf objects are static arrays, so their pointer values remain unchanged between calls to this slot. On each call, the counter is incremented and the text stored in the arrays is updated. A temporary QMessageLogger is then constructed using these pointers and a fixed line number and is used to log a string.

Result:

... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 1"
... npi.temp_2_cat some/file_2.cpp:11 func_2 | "Testing Context with Counter: 2"
... npi.temp_3_cat some/file_3.cpp:11 func_3 | "Testing Context with Counter: 3"
... npi.temp_4_cat some/file_4.cpp:11 func_4 | "Testing Context with Counter: 4"
... npi.temp_5_cat some/file_5.cpp:11 func_5 | "Testing Context with Counter: 5"
... npi.temp_6_cat some/file_6.cpp:11 func_6 | "Testing Context with Counter: 6"
... npi.temp_7_cat some/file_7.cpp:11 func_7 | "Testing Context with Counter: 7"

The same test was also performed (in E145_Log using Qt 6.8.3) using caches that generated their hashes from the pointer values themselves. Because the pointer values did not change between calls to the slot, the output was:

... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 1"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 2"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 3"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 4"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 5"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 6"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 7"

Conclusion: The texts are stored correctly in the caches and are later retrieved by the log writer thread using their assigned indices. When pointer values are used as cache keys, the text found during the first lookup is stored and reused because the pointer addresses remain unchanged. As a result, every subsequent log incorrectly contains the first category, file, and function texts. This test demonstrates that pointer-based cache keys are unreliable because the text stored at a stable address can change. Content-derived keys correctly distinguish the updated contexts. Hashing pointer values takes approximately 70% of the time required to hash the pointed-to text. However, because pointer-based caching is not reliable, it should not be used. Content-based caching remains beneficial because previously processed file and function texts do not need to be normalized again or copied into the text pools.

Note
The test using caches that generated their hashes from the pointer values themselves was not performed after moving to Qt 6.12.0. This is because this method is incorrect and previous test with this method done using Qt 6.8.3 was to just show why we need text based hash instead of easier pointer based hash.
Text sanitization

This test was performed to check the text sanitization. The text sanitization happens inside TextBuffer::appendChar_ function:

bool appendChar_(char chr) noexcept
{
// UTF-8 encodes non-ASCII Unicode characters using two to four bytes, all above
// 127. Since this function sanitizes one byte at a time, one Unicode character
// may therefore appear as "??", "???", or "????".
const auto uChr = static_cast<unsigned char>(chr);
if(chr == ' ' || chr == '\t' || chr == '\r' || chr == '\n' || chr == '\v' || chr == '\f') {
if(pos_ > beg_ && buf_[pos_ - 1] != ' ' && buf_[pos_ - 1] != '\n') {
if(!canAppend_(1u)) return false;
buf_[pos_++] = ' ';
}
return true;
}
if(!canAppend_(1u)) return false;
if(chr == '|') buf_[pos_++] = '/';
else if(uChr >= 32u && uChr <= 126u) buf_[pos_++] = chr;
else buf_[pos_++] = '?';
return true;
}

This means:

  • Tab, newline, etc. characters are converted to space.
  • Space is only added if:
    • previous character was not a space, and
    • current position is not the starting position.
  • The | is converted to / (since | is reserved for delimiter in log file).
  • Any character below 32, except recognized whitespace, or above 126 is replaced with ?.

Relevant test code:

  • Tab, newline, etc. characters are converted to space.
  • Leading spaces are removed (the spaces are added while formatting).
  • Multiple spaces are collapsed into one.
  • The | is converted to /.
  • Characters below 32, except recognized whitespace, or above 126 are replaced with ?.
Note
  • The character € is a non-ASCII Unicode character encoded using three UTF-8 bytes. Therefore, the category, file, and function texts contain ???. However, because the log message is a QString and is processed as UTF-16 code units through QStringView before TextBuffer::appendChar_ processes it, so the single UTF-16 code unit representing € produces one ? rather than three.
  • The | preceding the log message is added by the formatter so that the message is always separated from the other fields.
Fatal, critical and crash handling

Fatal and Critical logs were generated directly from MainWindow and from the stress-testing threads under extremely heavy loads.

  • All logs were written to the *.imp.log file as expected.
  • The *.imp.log file was generated only after the first fatal/critical log was generated.
  • The critical logs were also written to the normal *.log file.
  • Fatal logs resulted in immediate program termination, with a popup message and debug output, as expected.

Under heavy concurrent fatal logging, only the first fatal log displayed a popup and was written to the *.imp.log file. This behavior is expected and intentional. When multiple threads emit fatal logs concurrently, only the first thread to claim fatal ownership writes the fatal record and displays the popup. The other fatal threads wait for a fixed grace period then fail fast if the original thread hasn't done so already. This prevents competing fatal-handling paths and gives the owning thread sufficient time to write the log and display the popup. A guard is included to prevent the owning thread from waiting on itself if a re-entrant fatal log occurs on the same thread.

Limited crash-handling tests were performed. The crash handlers are installed, and crash logs are forwarded to the *.imp.log file. Some crash-handling tests could not be completed because Visual Studio intercepted the crash before the installed handlers could be invoked, for example, in the case of a stack overflow. Completing these tests would require running the executable outside Visual Studio together with all required supporting files.

Stuck display thread

If text is selected in the console, the WriteConsoleA or WriteConsoleW function used by the display thread can become blocked and fail to return. This is one of the main reasons why console output is handled by a dedicated display thread rather than the main thread. If the display thread is blocked while the application is shutting down, the user is asked whether to abandon the display thread and continue shutting down or to continue waiting. This works as expected. Terminating the process while the display thread is blocked has no adverse side effects and is supported by design.

Note
To perform this test, press Ctrl + F and search for text currently shown in the console. The matched text becomes selected, causing the display thread to become blocked.
