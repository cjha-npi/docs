GUI System

Introduction

The GUI system provides a centralized appearance and common widget behavior for the application's Qt Widgets interface. It combines dark, light and system-following themes with font-based sizing, custom control drawing and optional widget features configured through QObject custom dynamic properties.

The system works with standard Qt widgets rather than defining a separate widget toolkit. Shared styling and initialization are implemented in one application style, while individual controls request specialized behavior through the public interface. The current implementation also integrates with Windows application-theme settings and native window title bars.

Details

Gui.h declares the public interface in npi::gui, providing:

  • Theme selection and queries.
  • Access to GUI colors.
  • Property names in npi::gui::Props.

Application code uses this interface without depending on the private style class or its drawing helpers. Gui.cpp contains the implementation.

The central implementation class, GuiStyle, derives from QProxyStyle and uses Qt's Fusion style as its base. It selectively overrides widget initialization, geometry, drawing and event handling. Cases that are neither customized nor intentionally suppressed are delegated to the base style.

Its responsibilities are divided across the following mechanisms:

  • Widget polishing applies property-dependent setup, configures grouped controls and embedded item-view widgets, initializes theme-dependent icons and installs the required event filters.
  • Sizing and geometry overrides calculate control dimensions, icon sizes and content placement from font-based sizing data, keeping related controls visually consistent.
  • Drawing overrides provide control backgrounds, state indicators and specialized content, including completion-popup text and multi-level table headers.
  • Theme handling maintains dark and light drawing resources and updates the application palette and supported theme-dependent icons when the effective background changes.
  • Qt event filters handle widget-specific updates and hierarchy changes. A native event filter observes Windows application-theme changes when the selected theme follows the system; native title-bar colors are updated separately from widget painting.
Note
The GUI system does not emit a dedicated theme-change signal. A module handling user-requested theme changes can provide its own signal, but that alone will not cover automatic changes while following the system theme. To observe palette updates, a QObject-based event filter can monitor QEvent::ApplicationPaletteChange on the application or QEvent::PaletteChange on a widget. A palette change does not necessarily indicate a dark/light transition; use npi::gui::isDarkBackground() to determine the effective variant.

Private helper namespaces support these responsibilities:

  • make constructs drawing resources.
  • draw renders specialized content.
  • icon resolves and applies theme-dependent icons.
  • size calculates font-based dimensions.
  • item configures widget hierarchies and embedded item-view widgets.

The style is installed at application level. Initialization is scheduled through Qt's startup hook using Q_COREAPP_STARTUP_FUNCTION and deferred until application events are processed after QApplication construction; public theme-query and configuration functions can also initialize it on demand after QApplication construction. Once installed, Qt invokes the style's polishing, sizing and drawing functions as widgets are initialized, laid out and repainted. Event filters provide the additional updates required outside those calls.

Initialization

The GUI system initializes automatically after QApplication construction, when application events are processed. Application code does not construct GuiStyle or call the private initialization helpers directly. Initialization is handled by the private guiStyle() function in Gui.cpp. If the application already uses GuiStyle, this function returns the existing instance; otherwise, it initializes and installs a new instance and returns its pointer.

Warning
Attempting to initialize the GUI system before constructing QApplication produces a fatal log message and terminates the application.

There are two paths into initialization:

  1. Automatic: The Q_COREAPP_STARTUP_FUNCTION registers the private startup() function in Gui.cpp, which schedules initialization with QTimer::singleShot(0, qApp, ...). The callback runs when application events are processed, normally through exec().
    • The preferred startup pattern is to call QCoreApplication::processEvents() immediately after constructing QApplication in main(). This allows the scheduled GUI initialization to run before constructing the application's widgets.
  2. On-Demand: Every public GUI function except npi::gui::textColor() calls the private guiStyle() accessor. If the application does not already use GuiStyle, the accessor initializes and installs it before completing the requested operation. Even a query such as npi::gui::theme() can therefore initialize the GUI system. npi::gui::textColor() is independent of GUI initialization.
Note
  • Both paths use the same accessor. If GuiStyle is already installed, it is reused; an earlier public API call does not cause the deferred startup callback to create a second style.
  • Calling QCoreApplication::processEvents() at this point can also run other pending startup callbacks. The call is made explicitly by application code, not by the GUI startup hook. It does not guarantee completion of initialization work that those callbacks defer to a later round of event processing.

When a style must be installed, initialization performs the following work:

  1. Registers the bundled technical fonts, as described in Technical Font.
  2. Constructs the Fusion-based GuiStyle, captures the current application font and its sizing data, creates dark and light theme resources, and loads built-in control icons.
  3. Resolves the initial Theme::System selection against the current Windows application-theme setting, applies the corresponding palette and installs the native event filter.
  4. Installs the style on QApplication through setStyle().

For predictable initial sizing and appearance, initialize the GUI before constructing the main interface. Use the automatic path for initialization:

#include <QApplication>
#include "MainWindow.h"
int main(int argc, char* argv[])
{
QApplication app(argc, argv);
QCoreApplication::processEvents(); // GUI initializes
MainWindow window; // Main interface
window.show();
return app.exec();
}

Custom Properties

npi::gui::Props supplies the names of QObject custom dynamic properties understood by the style. Use these constants with setProperty(), for example widget->setProperty(npi::gui::Props::WheelToParent_, true);, instead of repeating their underlying strings. The strings, such as npi_WheelToParent, are also listed so the properties can be configured in Qt Designer. Use the documented value type and apply properties before the widget is polished; Gui.h defines the public contract for each property.

Note
  • Apply these properties before the widget is polished. If that timing cannot be ensured, manually polish the widget after setting the property, for example widget->style()->polish(widget).
  • npi::gui::Props::ButtonColorDisplay_ is the only property whose value is intended to change dynamically after initialization. Set it before polish; its QColor value may then be updated at runtime.
  • Other properties may appear to work when applied after polish because an event filter is already installed, a cached size hint is recalculated or the property is read during painting. Do not rely on these incidental conditions instead of following the documented initialization requirements.
Warning
Do not use the implementation's npi_gui_private_* properties from application code.

Usage

The snippets below assume an existing QApplication, an initialized GUI system and, where used, an owning QWidget* parent. Include Gui.h and the Qt headers for the classes used, including QVariant for property values. Add the constructed widgets to the application's layouts as appropriate.

  • Select a theme or obtain colors through the public interface:
    npi::gui::setTheme(npi::gui::Theme::Dark);
    const bool dark = npi::gui::isDarkBackground();
    const QColor buttonColor = npi::gui::surfaces().raised_;
    const QColor lightBase = npi::gui::surfaces(false).sunken_;
    const QPalette currentPalette = npi::gui::palette();
    const QColor textColor = currentPalette.color(QPalette::Active, QPalette::Text);
    const QColor lightHighlight = npi::gui::palette(false).color(QPalette::Active, QPalette::Highlight);

    auto* passwordEdit = new QLineEdit{parent};
    passwordEdit->setProperty(npi::gui::Props::PasswordLineEdit_, true);
    passwordEdit->setProperty(npi::gui::Props::WheelToParent_, true);
  • For theme-dependent action icons, set the resource name before adding the action to a menu or toolbar. This example assumes the corresponding save.png resources exist:
    auto* menu = new QMenu{parent};
    auto* saveAction = new QAction{"Save", menu};
    saveAction->setProperty(npi::gui::Props::IconName_, QString{"save"});
    menu->addAction(saveAction);
  • For a color display, set the property before polish and update its value when the displayed color changes:
    auto* colorDisplay = new QPushButton{parent};
    colorDisplay->setProperty(npi::gui::Props::ButtonColorDisplay_, QColor{40, 120, 200});
    // Later, after normal widget initialization:
    colorDisplay->setProperty(npi::gui::Props::ButtonColorDisplay_, QColor{200, 80, 40});
    Note
    Keep the color display enabled when the actual color is required; disabling it displays the color in grayscale. Configure it as a non-interactive display, without an application click action.
  • Create a button-group base with its layout and direct children before polish:
    auto* modeGroup = new QWidget{parent};
    modeGroup->setProperty(npi::gui::Props::ButtonGroupBase_, true);
    auto* modeLayout = new QHBoxLayout{modeGroup};
    auto* modeA = new QPushButton{"Mode A", modeGroup};
    auto* modeB = new QPushButton{"Mode B", modeGroup};
    modeLayout->addWidget(modeA);
    modeLayout->addWidget(modeB);
    modeGroup->ensurePolished(); // Initialize the exclusive group and make its buttons checkable.
    modeA->setChecked(true); // Select the initial button after group initialization.
  • For a widget installed in a table cell, mark the root before assigning it to the view. This example assumes table already has cell (0, 0):
    auto* cellWidget = new QWidget;
    cellWidget->setProperty(npi::gui::Props::ItemViewWidget_, true);
    auto* cellLayout = new QHBoxLayout{cellWidget};
    cellLayout->setContentsMargins(0, 0, 0, 0);
    auto* cellEdit = new QLineEdit{cellWidget};
    cellLayout->addWidget(cellEdit);
    table->setCellWidget(0, 0, cellWidget);
    The table takes ownership of the installed widget. Its descendants inherit the style's item-view configuration; they do not need their own public ItemViewWidget_ property.
  • If a property must be applied to an already polished widget, explicitly apply the required initialization. For example, given an existing QPushButton* button:
    button->setProperty(npi::gui::Props::WidthSameAsHeight_, true);
    button->style()->polish(button);
    // Invalidate a cached size hint when immediate recalculation is needed.
    QEvent styleChange{QEvent::StyleChange};
    QCoreApplication::sendEvent(button, &styleChange);
    button->updateGeometry();
    button->update();
    This example also requires the QStyle, QEvent and QCoreApplication headers.
    Note
    Manual polishing applies the property-dependent setup, while the QEvent::StyleChange event requests recalculation of cached style-dependent geometry. Neither operation undoes earlier configuration or makes every property safely reversible. Prefer setting properties before the initial polish, especially those that create actions, replace validators or modify widget hierarchies.

Application Font

The GUI uses the default application font provided by Qt and the operating system rather than assigning a custom application-wide font. On Windows, this will normally be the system UI font, such as Segoe UI, but the GUI does not explicitly depend on or hard-code a particular font family.

Atkinson Hyperlegible and Atkinson Hyperlegible Next were evaluated as possible application fonts. They have an important advantage for technical software: visually similar characters such as O and 0, or I, l, and 1, are intentionally designed to be easily distinguishable. Using Atkinson throughout the GUI would therefore reduce the need to assign a separate font such as JetBrains Mono to controls where character clarity is important.

However, testing showed several disadvantages that make Atkinson unsuitable as the general application font:

  • The tested font files did not cover all required UI symbols. For example, the tested Atkinson Hyperlegible font lacked U+25CF (●), used for password masking in that configuration. The first fallback lookup under Qt 6.8's Windows DirectWrite backend coincided with handled CacheOverflowException exceptions and a noticeable one-time delay (see Bug: Font CacheOverflowException).
  • In the tests, the Atkinson fonts had substantially different vertical metrics from Segoe UI at the same nominal point size. Their reported height, ascent and leading differed, as did their perceived glyph size and visual alignment. Consequently, mathematically centered text could still appear vertically offset.
  • Using a different point size, such as Atkinson Hyperlegible Next at 10 pt instead of 9 pt, can provide a perceived text size closer to the default font, but it does not remove the differences in vertical metrics. Correcting this would require font-specific optical offsets and potentially different adjustments at different font sizes.
Note
Keeping the system-provided font allows platform settings, including accessibility text sizing as reflected by Qt at startup, to influence the initial UI. The style captures its sizing baseline during initialization and does not implement a complete runtime refresh when Windows font settings change. Restart the application after such a change. Replacing the font family while retaining the system-derived point size does not guarantee equivalent visual dimensions.

Keeping the default font avoids the application-wide font-specific adjustments encountered in those tests and preserves the platform-selected starting point for sizing and appearance. It does not guarantee that every character exists in the primary font or that font fallback will never be needed.

The application consequently leaves the normal GUI font family unchanged and uses the font supplied by Qt at startup. Specialized fonts should only be applied where their specific properties are required. For example, JetBrains Mono is available for technical values, identifiers, code, hexadecimal data, or other content where fixed-width alignment or unambiguous character shapes are more important than native GUI appearance. Its bundled font files are loaded automatically during GUI initialization, and the style already corrects its vertical text alignment in several drawing paths, including line-edit contents (see Technical Font).

This keeps the general GUI consistent with the operating system while limiting custom font handling to controls where it provides a clear functional benefit.

Technical Font

JetBrains Mono is the bundled technical font, available in addition to the normal application font. Its monospaced design supports fixed-width alignment, while distinct shapes for characters such as 0 and O, or 1, l and I, make technical content easier to read accurately. See the JetBrains Mono design overview for examples of these character differences.

Use it selectively for content such as:

  • Identifiers, serial numbers and other values where confusing similar characters could cause mistakes.
  • Hexadecimal values, memory addresses and byte sequences.
  • Code, expressions and plain-text output that benefits from fixed-width alignment.

Font availability is managed by the GUI system:

  • During GUI initialization, the private initFont() function registers the bundled Regular, Bold, Italic and Bold-Italic files from :/fonts/ with Qt's application font database, before GuiStyle is constructed. A separate operating-system font installation is not required.
  • Registration makes the font available to the application; it does not replace the default application font or assign JetBrains Mono to widgets automatically.
  • The loading pass runs once. A failed font load produces a warning and is not retried on later initialization calls.

To use the font, copy the target widget's font, change its family to "JetBrains Mono", and assign it back to the widget. This preserves the existing font size instead of introducing a hard-coded technical-font size. Bold and italic can be requested through the usual QFont settings; use the same family name for all variants. See QFont for the font-selection API.

The following example assumes that QApplication exists, GUI initialization has completed as described in Initialization, and parent is the owning widget:

auto* lineEdit = new QLineEdit{parent};
QFont monoFont{lineEdit->font()};
monoFont.setFamily("JetBrains Mono");
lineEdit->setFont(monoFont);

The style compensates for JetBrains Mono's higher visual alignment by shifting text down by one pixel in several places:

  • GuiStyle::drawItemText() adjusts text drawn through that style function.
  • draw::adjustedText() applies the same correction in custom drawing paths, including button labels, combo-box text and header labels.
  • GuiStyle::subElementRect() adjusts the line-edit contents rectangle.
Note
  • The alignment corrections recognize "JetBrains Mono" in the font's requested family list. Use the family name exactly as shown in the example.
  • The affected drawing paths apply the correction automatically; do not add another vertical offset when using those paths.
  • These corrections do not change the font's metrics globally. Custom painting or text rendering that bypasses the listed paths must be checked separately for visual alignment.

Themes and Colors

Theme selection and the effective background are separate concepts:

  • npi::gui::Theme::Dark selects the application's dark variant.
  • npi::gui::Theme::Light selects the application's light variant.
  • npi::gui::Theme::System, the initial selection, follows the Windows application-theme preference. It selects one of the application's own palettes; it does not copy the complete Windows theme or accent-color configuration.
  • npi::gui::theme() returns the selection, while npi::gui::isDarkBackground() reports whether the effective variant is dark. For example, the selection can remain System while the effective background changes from light to dark.

The system preference is read from AppsUseLightTheme under the current user's Windows personalization settings; a missing value defaults to light. While following the system, the native event filter rechecks that preference on the relevant WM_SETTINGCHANGE notification. Explicit Dark and Light selections do not follow those notifications.

Changing the selection always records the new choice, but the palette and dynamic icons are refreshed only when the effective dark/light variant changes. For example, selecting Dark while System already resolves to dark changes the selection without rebuilding the same appearance.

Note
Theme preference persistence is the caller's responsibility; this module does not save the selection.

Use the public surface and palette functions when custom content must match the GUI:

  • npi::gui::surfaces() returns the currently effective variant's surface colors:
    • sunken_: recessed backgrounds, such as text-entry controls.
    • normal_: the main window/background surface.
    • raised_: elevated backgrounds, such as buttons.
  • npi::gui::palette() returns the GUI system's application palette for the currently effective variant, including text, highlight and disabled-state colors.
  • Passing true to either function selects the dark variant; passing false selects the light variant, independently of the configured theme selection.

The surface and palette functions return copies. There is no public surface setter; changing a returned copy does not modify the GUI system's stored theme resources.

Note
  • Returned values do not update automatically when the theme changes. Custom widgets that cache them must refresh their cached resources and repaint when the effective theme changes.
  • QPalette::Button and QPalette::Base intentionally contain the same colors as QPalette::Window. To match custom button and text-entry backgrounds, use the corresponding Surfaces::raised_ and Surfaces::sunken_ values instead.
  • npi::gui::palette() returns the GUI system's generated theme palette, not an arbitrary palette subsequently assigned to the application or an individual widget. Use the widget's own palette when custom painting should respect its local palette overrides.

npi::gui::textColor(background) selects black or white text using a weighted RGB brightness heuristic. It does not guarantee a particular contrast ratio and ignores alpha; for a translucent background, pass its final composited color. The helper does not require GUI initialization.

Native title-bar backgrounds are updated separately from widget painting. On QEvent::Show and QEvent::PaletteChange, the style requests the top-level widget's QPalette::Window color through DWM, provided a native window handle is available. This customization does not implement title-bar controls or set the caption text color.

Theme-Dependent Icons

An icon name is a resource basename without a path or extension. For an object whose npi::gui::Props::IconName_ property contains "save", lookup proceeds in this order:

  1. :/icons/dark/save.png or :/icons/light/save.png, according to the effective variant.
  2. :/icons/save.png if that theme-specific resource does not exist.

The opposite theme's directory is not searched. Supply Qt resources at these paths; the mechanism does not load arbitrary filesystem paths or operating-system theme icons.

For buttons and actions, QIcon::Off and QIcon::On states are resolved independently:

  • npi::gui::Props::IconName_ supplies the Off-state resource, and npi::gui::Props::IconOnName_ supplies the On-state resource. Providing an On-state icon does not itself make the button or action checkable.
  • The original icon is stored on the first dynamic-icon update. If a state's name is empty or its resource is unavailable, that state falls back to the stored original icon's available QIcon::Normal pixmaps.
  • If both names are empty, no dynamic-icon update is performed.
  • A non-empty name for which neither resource exists produces a warning.

A QLabel uses only npi::gui::Props::IconName_. Failed lookup leaves its existing pixmap unchanged, which may be the pixmap from the previous theme.

Note
The original-icon fallback copies available QIcon::Normal state pixmaps; it does not preserve every custom icon mode or icon-engine behavior.

During polishing, the style initializes:

  • Property-based icons on push buttons and tool buttons.
  • Property-based pixmaps on labels.
  • Dynamic icons on actions already associated with the widget.
  • The dynamic icon of a tool button's default action.

Actions added later to monitored menus, menu bars, toolbars and tool buttons are initialized through QEvent::ActionAdded.

Note
Set an action's icon properties before adding it to its host. An unattached QAction is not discovered merely because it has a QObject parent.

On effective theme changes, registered actions are updated, and existing buttons and labels are checked for property-based icons. The action registry is non-owning and removes entries when actions are destroyed. Resource names are intended to remain fixed after setup; switching theme changes which resource is used, not the property values.

For a tool button driven by a default action, normally put the dynamic-icon properties on the action so there is one source for its icon. The separate menu-drawing customization also recolors named edit-* icons to match enabled and disabled menu text; this is independent of resource-name lookup.

Grouped and Embedded Widgets

Grouped controls and embedded item-view widgets share background-suppression helpers but have different purposes:

  • A WidgetGroupBase_ paints one rounded button-colored surface. Its widget descendants are configured to let that surface show through instead of drawing their own backgrounds.
  • A ButtonGroupBase_ paints the shared surface and manages direct button children through an exclusive QButtonGroup. An existing direct child QButtonGroup is reused; otherwise one is created. Choose an initial checked button explicitly if the application requires one.
  • An ItemViewWidget_ root and its widget descendants are configured for transparent backgrounds inside the owning view. QSizePolicy::Fixed vertical size policies are changed to QSizePolicy::Expanding so nested controls can fill their cell. Standard control-height and square-size adjustments are bypassed there.

Create a group base's layout before it is polished. Initialization sets that layout's margins and spacing to zero, but a layout added afterward does not receive those changes automatically.

The style installs hierarchy filters so newly added widget descendants receive the appropriate configuration. QEvent::ChildAdded handling is deferred until events are processed because the notification can arrive during child construction; guarded pointers prevent access to objects deleted before the callback. For overlapping item-view and group configuration, item-view handling is applied first.

Mark only the root explicitly assigned to an item view. Do not mark the entire view, its viewport or temporary Qt-created delegate editors as application-supplied cell widgets. Selection highlighting is suppressed beneath an index widget whose root has ItemViewWidget_, keeping embedded text readable.

Warning
These configurations are not reversible reparenting operations. Widgets may be added or removed, but a configured group or cell-widget hierarchy is not intended to be moved elsewhere and reused as an ordinary unconfigured hierarchy.

Custom Drawing and Sizing

The custom style coordinates geometry and painting rather than treating each control independently. The main drawing responsibilities are:

  • Rounded button and text-entry backgrounds, pressed feedback, bottom focus indicators, translucent default-button overlays and grouped-control surfaces.
  • Push-button text/icon/menu layout, checkboxes, radio buttons, spin-box arrows and scrollbar controls.
  • Menu, combo-box popup and tooltip backgrounds using a raised_ fill with a sunken_ outline, plus menu-item highlights and selected item-view text backgrounds.
  • Tree-branch icons, compact splitter grips and progress-bar tracks. Progress fill drawing remains delegated to Fusion so orientation, inverted appearance and busy mode are retained.
  • Specialized table headers and completion-popup text, described in the following sections.

The normal Fusion drawing is retained where no customization applies. Some elements are intentionally left unpainted to avoid duplicate backgrounds, frames or combo-box drawing. New drawing code must preserve the painter state when changing pens, brushes, transforms, clipping or render hints.

The standard height calculation uses the application font's attributes with the widget font's configured pixel or point size. This keeps controls aligned when a widget uses another family, such as JetBrains Mono, at the same size. The current calculation:

  • Normalizes the minimum height to at least 12 and the maximum to at least that minimum.
  • Adds 8 to the measured font height for borders and minimum icon-edge spacing, then takes the larger of that result and the normalized minimum height.
  • Rounds up to a heightQuantum of 4, then clamps to the maximum height. A restrictive maximum can therefore produce a height that is not a multiple of 4.
  • Derives icon dimensions from the resulting height, border width and height-dependent edge spacing.

These are Qt widget-coordinate dimensions, not a promise of a fixed number of physical display pixels. Standard heights apply to push buttons, tool buttons, line edits, combo boxes and spin boxes with a QSizePolicy::Fixed vertical size policy. Embedded item-view widgets, internal complex-control line edits and line-edit tool buttons retain Qt-controlled sizing.

Square sizing is automatic for menu-free icon-only push buttons and menu-free tool buttons displaying only an icon or arrow. WidthSameAsHeight_ requests it explicitly for other applicable controls. It changes the size hint, not the layout's allocation, and minimum/maximum widths can prevent a square result.

Other geometry adjustments include font-scaled tree indentation and indicator sizes, extra space and even heights for item-view items, compact menu items, and push-button widths that account for text, icons and menu arrows. Multiline push-button text adds a font-line height for each line after the first.

Note
The style caches application sizing data at construction and reuses it when the widget's configured font size and height limits permit. Qt widgets may also cache size hints. When a setup change does not invalidate that cache, a QEvent::StyleChange event can request recalculation; repainting alone does not recalculate layout geometry. See Usage.

Table and Tree Headers

The multi-level header renderer applies to QTableWidget, not arbitrary QTableView models. It reads normal model header text, including Qt's default labels when explicit header items are absent:

  • Horizontal labels use newline-separated levels, ordered top to bottom: "Input\nVoltage".
  • Vertical labels use the exact separator " > ", including its spaces, ordered left to right: "Group A > Channel 1".
  • Empty parts are ignored. Shorter hierarchies are aligned at the deepest level by prepending empty parent levels; blank separators cannot reserve a level.
  • The maximum depth is determined by non-hidden sections.

Equal labels merge across adjacent sections in non-hidden visual order only while all their parent levels also match. Moving or hiding sections therefore affects which labels are adjacent and can merge. Off-screen but non-hidden sections still participate in grouping.

For example, in a table with at least three columns:

table->setHorizontalHeaderLabels({
"Input\nVoltage", "Input\nCurrent", "Output\nVoltage"
});

The first two columns share the upper label Input. The third belongs to Output; its Voltage label does not merge with Voltage under Input. For a table with at least two rows, the analogous vertical format is:

table->setVerticalHeaderLabels({
"Group A > Channel 1", "Group A > Channel 2"
});

Selection and current-cell emphasis are computed separately, taking cell spans and hidden sections into account. A header group is marked when it contains the relevant non-hidden row or column span. Header-item enabled flags control disabled text appearance.

Note
A merged parent uses disabled text styling only when all its child sections are disabled. This controls appearance, not whether the header section accepts input.

The renderer paints the full header viewport once per full paint. A viewport event filter promotes partial paints to full updates so merged sections can be drawn together. Horizontal levels share the available height; vertical parent levels are positioned using text widths. Provide sufficient header height or width for the chosen hierarchy, especially after font or label changes.

These are visual groups, not merged QHeaderView interaction regions or model sections. Normal logical indices and header interactions remain separate. QTreeWidget uses a simpler header: it draws the current column's text in bold with a bottom line, without interpreting the table hierarchy separators.

Warning
The custom table and tree header paths do not draw standard header icons or sort arrows.

Completion Popups

Recognized QCompleter popup items emphasize the completion suffix:

  • A visible matching prefix is identified using the completer's case-sensitivity setting. Its displayed casing comes from the model's text, not from the user's typed prefix.
  • In ordinary, non-highlighted items, the prefix is dimmed while the suffix keeps the normal text color. Selected or hovered items use normal text coloring.
  • When space is limited, the suffix is prioritized by eliding or dropping the prefix first. If the suffix itself does not fit, it is right-elided. Exact completions with no suffix are right-elided normally.
  • Items without a visible matching prefix use normal text coloring.

The helper retains the base style's non-text item drawing and lays out the customized text within the intersection of the text rectangle and the painter's existing clip. It changes presentation only; completion matching, filtering and insertion remain QCompleter's responsibility.

Note
Recognition requires the completion model to be owned by its QCompleter and the widget passed to the style to be that completer's popup. Custom delegates, proxy arrangements or popup implementations that bypass this path may retain ordinary item drawing.

Limitations

  • The current implementation is Windows-specific and requires Qt Widgets and the Fusion style. It does not provide a Qt Quick style or a portable native-theme abstraction.
  • Native caption-color customization requires Windows support for DWMWA_CAPTION_COLOR, documented from Windows 11 build 22000. If the caption-color request fails, a warning is logged; the GUI's custom widget painting remains in use. See Microsoft's DWM attribute documentation.
  • Perform GUI setup and widget changes on the GUI thread, following Qt's GUI-thread requirements. This module does not provide synchronization or cross-thread dispatch for its public functions.
  • Keep one GuiStyle installed for the application's normal lifetime. Replacing the application style is not a supported reset procedure: private widget markers, installed configuration and references such as the shared validator are not designed as a reversible teardown/rebuild interface.
  • Runtime application-wide font changes are not supported by the sizing-cache design. In particular, changing Windows text-size settings is not handled as a complete font-and-layout refresh; restart the application to establish a new consistent baseline.
  • Custom palettes, style sheets and delegates can override or bypass parts of the centralized appearance. Neither a palette change nor an arbitrary custom widget guarantees that every surface follows the GUI's dedicated colors.
  • Property initialization may overwrite existing widget configuration. Observe the per-property restrictions, do not use internal properties, and do not repurpose configured group or item-view descendants as ordinary widgets.
  • PasswordLineEdit_ is tailored to the application's restricted input format. It is unsuitable for a field that must accept arbitrary Unicode or a different length policy; programmatically assigned values still require appropriate application validation.
  • The custom header renderer is specific to QTableWidget and QTreeWidget. Visual header groups do not implement group-level sorting or resizing, and header icons/sort arrows are not drawn by these paths. Full-viewport header painting also warrants performance checks for large tables.
  • Font-specific optical correction is deliberately limited to the paths described in Technical Font. Other families, custom text painting and unusual font sizes require visual verification.
  • Integration with Qt internals must be rechecked on Qt upgrades, particularly internal line-edit naming, the clear-action object name, combo-box popup behavior and completion-model ownership assumptions.

Diagnostics and Maintenance

The GUI implementation logs lifecycle and theme activity, and warns when optional customization cannot be applied. Useful cases to check include:

  • Missing theme-dependent icon resources: check the basename and Qt resource aliases for both theme variants and the common fallback.
  • Bundled font-load failures: check the four JetBrains Mono resources. The loading pass is not retried automatically.
  • Missing line-edit clear actions: the lookup depends on Qt's internal object and class names, and the customization attempt is recorded even when it fails.
  • Native caption-color failures: the warning includes the widget name and HRESULT for platform diagnosis.

When changing the style or upgrading Qt, check:

  • Both themes and live system-theme switching.
  • Enabled, disabled, focused, pressed and checked controls.
  • Normal and technical fonts, display scaling and larger text.
  • Grouped and embedded widgets, including dynamically added children.
  • Table headers with hidden or moved sections and cells spanning multiple rows or columns.
  • Completion popups with exact matches, case-insensitive matches and narrow widths.

Keep Gui.h, implementation comments, examples and this page consistent. The historical font investigation below records a separate experiment and should not be treated as a list of initialization steps currently performed by Gui.cpp.

This section records the earlier Atkinson application-font experiment. The current Gui.cpp does not select Atkinson, warm up font fallback or override the password-mask character. The examples below are optional experimental workarounds, not part of the normal initialization sequence.

While trying to use Atkinson Hyperlegible as the application font, I noticed that if a password line edit had its echo mode set to Password and a character was entered, or if characters had already been entered and the line edit's echo mode was changed from Normal to Password, exactly 4 exceptions were shown in the debugger output. Exception thrown at 0x00007FF99B4F187A in E118_Main.exe: Microsoft C++ exception: CacheOverflowException at memory location 0x00000099324F2CC0.
Exception thrown at 0x00007FF99B4F187A in E118_Main.exe: Microsoft C++ exception: CacheOverflowException at memory location 0x00000099324F2CC0.

The observations in that test were:

  • The exception type is CacheOverflowException.
  • Four exceptions appeared on the first fallback lookup.
  • The application continued normally afterward, without an unhandled exception or observed failure.
  • Subsequent missing-character rendering did not reproduce the exceptions during that run.

The count and timing are observations, not guarantees across Qt, Windows or font versions. In the same experiment, forcing the older GDI backend avoided the exceptions:

int main(int argc, char* argv[])
{
qputenv("QT_QPA_PLATFORM", "windows:fontengine=gdi");
QApplication app{argc, argv};
// ...
}

This behavior is consistent with initialization or caching in the DirectWrite fallback path, but the debugger messages alone do not establish the exact internal cause. The important practical result was a one-time delay followed by normal rendering in the tested run.

Note
The GDI backend is a legacy alternative. Do not switch the whole application's font backend solely to silence handled debugger exceptions without also evaluating rendering and font-feature differences.

One possible mitigation for a reproducible first-use delay is to trigger the relevant fallback during startup, before the main UI is shown. This moves the work earlier; it does not fix the backend or guarantee that every later fallback path is warmed. The following experiment renders a character known to be missing from the tested primary font:

void warmUpFontFallback()
{
QImage image{32, 32, QImage::Format_ARGB32_Premultiplied};
image.fill(Qt::transparent);
QPainter painter{&image};
painter.setFont(qApp->font());
// U+25CF BLACK CIRCLE is missing from the tested Atkinson font.
painter.drawText(image.rect(), Qt::AlignCenter, QString{QChar{0x25CF}});
}

Qt 6.8 introduced application-defined fallback families; the optional Segoe UI preference below still requires that font to be available:

// Add Segoe UI as an explicit fallback font.
// This is optional and makes Segoe UI preferred for missing Common/Latin glyphs.
QFontDatabase::addApplicationFallbackFontFamily(
QChar::Script_Common,
"Segoe UI");
// Set the application font.
// Make sure Atkinson Hyperlegible has already been added to the font database.
QFont appFont{qApp->font()};
appFont.setFamily("Atkinson Hyperlegible");
appFont.setPointSize(10);
qApp->setFont(appFont);
// Trigger the relevant font fallback before showing the UI.
warmUpFontFallback();
// Continue with the rest of the application initialization.
...

A separate experiment can avoid this particular missing glyph by selecting a password-mask character present in the chosen font. The following possible styleHint() override is not implemented in the current GuiStyle:

int styleHint(
QStyle::StyleHint hint,

const QWidget* widget = nullptr,

{
switch(hint) {
case SH_LineEdit_PasswordCharacter:

In the tested Atkinson font, U+2022 (•, BULLET) was available while U+25CF (●, BLACK CIRCLE) was not. Recheck glyph coverage and behavior before applying either workaround to another font or runtime version.
