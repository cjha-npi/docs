Overview

Introduction

The Dev Hub is the shared developer area. It contains Markdown (.md) files that describe everything that supports development work but is not part of the product/API documentation itself. Dev Hub is for:

  • How we work?
  • How we support development?

The Dev Hub is a branch that is common to all projects. Do not place project's design/architecture, API docs, or feature documentation in this branch, those belong under the normal Doxygen sections (Namespaces, Concepts, Classes, etc.) or under the two project specific branches have been created: Dependencies and Architecture.

Special Branches

Special branches are additional branches injected into the root navigation structure of the generated Doxygen output. These are Markdown-only branches, meaning they contain only Markdown (.md) files, with image files added only when needed. Each branch fills a gap in the standard Doxygen-generated output and provides a more complete documentation structure.

Doxygen processes Markdown (.md) files like other input files. The HTML page name generated for a Markdown page is derived from its page ID. doxy-plus.js filters these generated pages using known page ID prefixes and then creates special branches in the root navigation structure.

There are two types of special branches:

  1. Project-independent branches
  2. Project-dependent branches
Note
These branches do not appear if there are no pages to be shown including Automatic Pages if any.

Limitations

Limitations come from external sources, such as Doxygen behavior or Markdown structure.

Markdown Page Hierarchy

Doxygen does not determine the Markdown page hierarchy or tree structure from the source folder structure. Instead, it builds the Markdown page hierarchy using \subpage links between pages. This means a good hierarchy depends on correctly linking pages with \subpage, regardless of where the Markdown files are physically located, as long as they are included in the Doxygen INPUT path.

Constraints

Constraints come from internal design choices and from how the generated data is post-processed in doxy-plus.js.

Tree Node Restriction

The navigation tree node structure generated by doxy-plus.js allows either a link or a list of child nodes, but not both. If a node has both, the child nodes take priority. This design choice is deliberate. It gives each node a single responsibility: either expand/collapse or navigate on click. As a result, the user interface remains simpler and more predictable.

  • In the root URL-pathname navigation tree, if a node has both a link and child nodes, the node's own link is discarded and the child nodes take priority.
  • In the page-local hash navigation tree, if a node has both a link and child nodes, the node's own link is moved into a newly created child node named Overview. This Overview node is inserted as the first child.

Starting Point

To discover a special branch, doxy-plus.js needs a known starting point. This starting point is a fixed page ID that acts as the top-level contents page for that branch.

The starting point is not discovered from the folder structure. It is hardcoded in doxy-plus.js and must exist in the generated Doxygen output. From this page, doxy-plus.js follows the \subpage chain to discover all pages that belong to the branch.

In practice, the starting point should be the page ID of the top-level _contents.md file for that branch. This file defines the first visible level of the branch. After the root navigation tree has been generated, the link to the _contents.md page itself is discarded, and only its child structure is kept.

If the starting point is missing, incorrectly named, not included in the Doxygen INPUT path, or does not contain the expected \subpage links, the branch cannot be generated correctly.

Setup

This section describes how to create and maintain a special branch.

A special branch should have:

  1. A dedicated parent folder.
  2. A branch-specific page ID prefix.
  3. A branch-specific contents ID prefix.
  4. A top-level _contents.md file.
  5. A hardcoded top-level contents page ID in doxy-plus.js.
  6. Markdown pages linked through \subpage.

The recommended setup flow is:

  1. Create the parent folder for the branch.
  2. Add the folder to the Doxygen INPUT path if it is not already included.
  3. Create a top-level _contents.md file.
  4. Assign the top-level contents page ID using the branch-specific contents ID prefix.
  5. Add child pages using \subpage.
  6. Create the child Markdown pages.
  7. Use the branch-specific page ID prefix for all normal pages in the branch.
  8. Add or update the matching top-level contents page ID in doxy-plus.js.

Rules

  1. Allowed Characters: File names, folder names, page IDs, and section IDs should use only a-z, 0-9, and _.
  2. Page ID Prefix: All Markdown page IDs in a branch should use the branch-specific page ID prefix.
  3. Top-Level Contents ID: Due to Constraint > Starting Point, each branch needs a top-level contents page ID. This ID is hardcoded in doxy-plus.js and is used as the starting point for discovering the branch pages.

Recommendations

  1. Parent Folder: Place all files and folders for a branch inside a single parent folder. This provides one clear location for the branch files.

  2. Contents File: Due to Limitations > Markdown Page Hierarchy and Constraint > Tree Node Restriction, it is recommended to use a simple folder hierarchy and give each folder its own _contents.md file.

    This file defines the branch structure visible in the final output. It should contain only one page definition and a list of subpage links. After the root navigation tree has been generated, the link to this contents page is discarded.

    It is recommended that the page ID for each _contents.md file contains dir_ after the branch-specific page ID prefix. This clearly distinguishes contents pages from normal documentation pages.

  3. Section ID Prefix: To make references easier and avoid collisions, section IDs should use the parent page or section ID as their prefix, separated by two underscores. Example: page_id__section_id.

Contents File

The _contents.md file is a simple structure-only file. It should contain only a page ID, a title, and a list of subpages. Do not place normal text content inside a _contents.md file. After the root navigation tree has been generated, the link to the _contents.md page is discarded. This means any normal text content placed in a _contents.md file will be lost.

The _contents.md file should contain only:

  • A page ID using the \page marker.
  • A title, which is the text that appears after the page ID.
  • Subpage IDs using the \subpage marker.

Here is an example _contents.md file:

\page dp_dh_dir_settings Settings
\subpage dp_dh_basic_settings
\subpage dp_dh_expert_settings
\subpage dp_dh_dir_misc_settings

Here, Settings becomes the branch name. The pages with IDs dp_dh_basic_settings and dp_dh_expert_settings become child pages. The page with ID dp_dh_dir_misc_settings becomes a sub-branch of Settings only if it contains its own \subpage links. Otherwise, it is treated like any other child page.

Warning
A markdown page with no title will be discarded. So, this \page dp_dh_somepage Some Page is valid while \page dp_dh_somepage is invalid.

Project-Independent Branches

Project-independent branches do not vary from project to project. These branches should have their own dedicated parent folder where all Markdown files related to the branch are placed. Add this folder to the INPUT tag in the Doxyfile so that it is included when Doxygen generates the output.

These branches should also have their own image folder so that their images are not dependent on any specific project. The recommended structure is to place an _images folder inside the branch root folder. For example, if the root folder for the Dev Hub branch is E:/Doxy/_dev, the image folder should be: E:/Doxy/_dev/_images. Add this folder to the IMAGE_PATH tag in the Doxyfile.

Dev Hub Branch

The Dev Hub branch contains documentation pages related to the documentation setup, generated output customization, helper pages, known issues, and other development-support information.

Attribute Value
Page ID Prefix dp_dh_
Contents ID Prefix dp_dh_dir_
Top-Level Contents ID dp_dh_dir_dev_hub

Project-Dependent Branches

Project-dependent branches belong to a specific project and share resources with that project. The parent folders for these branches should be placed in the root of the project. These branches can share resources such as images with the project itself, so no extra branch-specific image folder is required. Also, if the full project folder and its subfolders are already included in the Doxygen INPUT path, these parent folders do not need to be added manually.

Dependencies Branch

The Dependencies branch contains documentation pages for external tools, libraries, assets, and other resources that the project depends on, but that are not part of the core project codebase. These resources are therefore not documented through the project source files alone (.h, .cpp, etc.).

Attribute Value
Parent Folder <project-root>/_dependencies (Recommended)
Page ID Prefix dp_dep_
Contents ID Prefix dp_dep_dir_
Top-Level Contents ID dp_dep_dir_dependencies

Architecture Branch

The Architecture branch contains documentation pages that explain important design decisions, internal structure, major systems, and why specific parts are implemented the way they are. In other words, it provides deeper insight into the architecture of the project.

Attribute Value
Parent Folder <project-root>/_architecture (Recommended)
Page ID Prefix dp_arch_
Contents ID Prefix dp_arch_dir_
Top-Level Contents ID dp_arch_dir_architecture

Automatic Pages

Some pages are generated automatically based on the usage of special predefined tags in the Doxyfile. These tags are defined using the ALIASES tag. The basic structure is:

ALIASES += "tag_name=\xrefitem page_id \"Source_Text\" \"Page_Title\""
Note
Use += instead of = when defining aliases in the Doxyfile, so that existing aliases are not overwritten.

The tag can then be used anywhere in the documentation. For example:

\tag_name Some text
\tag_name See page \ref some_page_id
\tag_name See section \ref some_section_id

All usages of the tag are collected on a single generated page with the page ID page_id. This is useful for collecting similar items in one place, such as requirements, bugs, warnings, notes, etc.

Note
  • The generated page is created only if the tag is used at least once in any file.
  • A tag created with \xrefitem also generates a visible entry at the place where the tag is used. If the local entry should not be visible, it must be hidden separately.

Project Required Page

This page collects all project-related content tagged as required, making important requirements easier to review, track, and maintain. When it appears, it is placed under the Dependencies branch. If the Dependencies branch does not exist, it is created automatically.

ALIASES += "dep_req=\xrefitem dp_dep_required \"REQUIRED\" \"Required\""
Note
Do not use this tag for files inside the Dev Hub branch.

Dev Hub Required Page

This page collects all Dev Hub content tagged as required, making important requirements easier to review, track, and maintain. When it appears, it is named Required and placed directly under the Dev Hub branch.

ALIASES += "dh_req=\xrefitem dp_dh_required \"REQUIRED\" \"Required\""
Note
Use this tag only for files inside the Dev Hub branch.

Dev Hub Bugs Page

This page collects all Dev Hub content tagged as bugs, making bugs easier to review, track, and maintain. When it appears, it is named Bugs List and placed directly under the Dev Hub branch.

ALIASES += "dh_bug=\xrefitem dp_dh_bugs \"BUG\" \"Bugs List\""
Note
Use this tag only for files inside the Dev Hub branch.

Adding Content to Markdown Files

This section shows how to add common content elements to Markdown files. These elements should be used where they improve navigation, readability, or explanation without making the page unnecessarily heavy.

Adding Links

The basic Markdown link syntax is:

[visible text](target)

For normal external links:

[Doxygen configuration manual](https://www.doxygen.nl/manual/config.html)

For Doxygen documentation pages, prefer \ref when linking to a page ID:

See \ref dp_doxyfile_full_code for the full file content.

With custom link text:

See \ref dp_doxyfile_full_code "Doxyfile full code".

More examples:

[Open Doxygen manual](https://www.doxygen.nl/manual/index.html)
[Open another Markdown file](other-file.md)
[Open a file in another folder](../docs/other-file.md)
[Go to a section in this file](#main-files)
[Go to a section in another file](other-file.md#main-files)

Adding Images

Images can be inserted in Markdown pages using the standard Markdown image syntax:

![Image caption](image-file-name.png)

Recommended setup:

  1. Create an _images/ folder at the root.
  2. In Doxyfile, add the image folder to IMAGE_PATH:
    IMAGE_PATH = ./_images
  3. Copy the image file into _images/. Example:
    _images/test_img.png
  4. Reference the image from a Markdown file:
    ![Image caption](test_img.png)

If needed, an explicit relative path can also be used:

![Image caption](_images/test_img.png)
Warning
Keep image basenames globally unique across all IMAGE_PATH folders; otherwise, collisions can occur.

Tips & Tricks

Hide xrefitem Text at Source

When a Doxygen alias based on \xrefitem is used, as described in Automatic Pages, Doxygen also shows the generated entry at the place where the alias is written.

For example, if the Markdown file contains:

\dh_bug Some text

the generated page shows the local BUG entry at that location:

This can sometimes be useful, but often it is not needed. To hide the local output, wrap the alias usage in an HTML element:

\htmlonly <div class="dp-hidden-xrefitem"> \endhtmlonly
\dh_bug Some text
\htmlonly </div> \endhtmlonly

This wraps the generated local output in an HTML div with the class dp-hidden-xrefitem. In doxy-plus.css, the following rule hides this class completely:

#doc-content > div > div.contents > div.textblock .dp-hidden-xrefitem {
display: none;
}
Note
The #doc-content > div > div.contents > div.textblock .dp-hidden-xrefitem selector is used so that this rule applies only to Markdown pages. Non-Markdown pages have #doc-content > div.contents instead of #doc-content > div > div.contents.

This removes the local output from the source page while still keeping the entry on the collected destination page, such as Dev Hub > Bugs List.

Add Line Gap When Needed

Text, especially numbered or bullet lists, may not show any visible gap between two items in the generated output from a Markdown file, no matter how many blank lines are placed between them. Sometimes additional separation is needed to make two items look visually separated. To add a visible gap, use:

- Point one
<div class="dp-markdown-list-gap"></div>
- Point Two

This creates a div with the class dp-markdown-list-gap between the two list items. In doxy-plus.css, the following rule assigns a height of one line to this item:

#doc-content > div > div.contents > div.textblock .dp-markdown-list-gap {
height: 1em;
}
Note
The #doc-content > div > div.contents > div.textblock .dp-markdown-list-gap selector is used so that this rule applies only to Markdown pages. Non-Markdown pages have #doc-content > div.contents instead of #doc-content > div > div.contents.
