OLD GUI System

Introduction

The GUI system provides a shared appearance and common behavior for the application's Qt Widgets interface. It supports dark, light and system-following themes, font-based sizing, custom drawing and optional widget features configured through dynamic properties.

The system uses standard Qt widgets with a customized Fusion style. Application code controls it through npi::gui, without depending on the private implementation.

Details

Public Interface

Gui.h provides the public interface:

  • Theme selection and queries.
  • Theme palettes and separate surface background colors.
  • Dynamic property names in npi::gui::Props.
Receiving Background

The GUI system does not provide a separate theme or background-change signal. Only on effective dark-to-light and light-to-dark transition, GuiStyle first sets the correct application palette and then sets the correct color scheme in application's style hints. Therefore, application code has three methods to receive such signal:

  1. Connect to application's style hints QStyleHints::colorSchemeChanged signal. The connection can be made like this
    connect(qApp->styleHints(), &QStyleHints::colorSchemeChanged, this, &Widget::onStyleHintsColorSchemeChanged_);
    The slot should be of the form:
    void onStyleHintsColorSchemeChanged_(Qt::ColorScheme colorScheme);
    On every dark-to-light or vice-versa application wide change the GuiStyle sets the corresponding Qt::ColorScheme::Dark or Qt::ColorScheme::Light which can be directly received in this slot.
  2. For a custom widget, listen to QEvent::PaletteChange in its changeEvent() then query npi::gui::isDarkBackground() to obtain the current dark/light background.
  3. Install an event filter on qApp and observe QEvent::ApplicationPaletteChange then query npi::gui::isDarkBackground() to obtain the current dark/light background.
Note
  • Palette-change events can occur for reasons other than a dark/light background change. Compare the current background with a previously stored value when only background changes matter.
  • Changing the selected theme without changing the effective background does not trigger an appearance refresh.
  • QStyleHints::colorSchemeChanged reports Qt color-scheme changes, not completion of the GUI's palette and icon updates. Use palette-change events when updating custom colors.
  • Observing these events must not prevent Qt's normal event processing.

Gui.cpp contains the implementation. Its private GuiStyle class derives from QProxyStyle and uses Fusion as its base. Drawing and behavior that are not customized are generally left to the base style.

The main responsibilities are:

  • Widget setup: Apply dynamic properties, configure grouped and embedded widgets, initialize icons and install event filters.
  • Sizing: Calculate consistent control heights, icon sizes and spacing from font sizes.
  • Drawing: Provide custom backgrounds, indicators, control layouts, completion items and multi-level table headers.
  • Themes: Update the application palette, tooltip palette, Qt color scheme and theme-dependent icons.
  • Events: Handle property updates, wheel forwarding, new actions and child widgets.
  • Windows integration: Observe Windows application-theme changes while System mode is selected.

The private helper namespaces organize the implementation:

Namespace Purpose

A shared QPointer<GuiStyle> tracks the application-owned style. This allows public GUI functions to find it even when an application stylesheet wraps the style. Initialization is scheduled during application startup and can also occur through an earlier public GUI function call. Both paths use the same private accessor.

Note
  • GUI system only customizes the client-area, no customization is done for window title bar or its frame.
  • When a QApplication exists and shutdown has not begun, any of the npi::gui functions initializes the GUI system if needed.
  • The GuiStyle object is owned by the application and tracked through a QPointer throughout its lifetime.
  • The style caches its initial font-based sizing data. Restart the application after changing Windows font settings to establish a new consistent sizing baseline.
  • Application-style initialization and widget polishing are separate steps. Set initialization properties from npi::gui::Props before the affected widget is polished. If necessary, apply them afterward with:
    widget->style()->polish(widget);
    Polishing does not undo earlier configuration or make every property reversible.
Warning
  • Use the public interface defined in npi::gui namespace only from application's main/GUI thread.
  • Before QApplication exists or after shutdown begins:
    • No GuiStyle object is created.
    • Theme-changing requests are ignored.
    • Queries return their documented fallback values.

Initialization

The GUI system initializes automatically. Application code does not construct GuiStyle or call its private setup functions.

There are two initialization paths:

  1. Deferred startup: Q_COREAPP_STARTUP_FUNCTION registers a startup callback that schedules GUI initialization with QTimer::singleShot(). Initialization runs when application events are processed after QApplication construction.
  2. Public function call: Any public function in npi::gui can initialize the GUI if it has not already been initialized.

Both paths use the private guiStyle() accessor and reuse the same style instance.

Preferred Startup

#include <QApplication>
#include "MainWindow.h"
int main(int argc, char* argv[])
{
QApplication app{argc, argv};
QCoreApplication::processEvents();
MainWindow window;
window.show();
return app.exec();
}

Call QCoreApplication::processEvents() immediately after constructing QApplication, before creating widgets. This processes pending events including deferred initialization for the GUI and other application structures. Without this explicit call or an earlier public GUI function call, deferred initialization normally runs when QApplication::exec() starts processing events.

Initialization Steps

Initialization performs the following work:

  1. Loads the bundled JetBrains Mono fonts.
  2. Constructs GuiStyle, saving the application font and sizing data, creating both themes and loading control icons.
  3. Installs the style using QApplication::setStyle().
  4. Sets the application icon, applies the initial System theme and installs the native event filter.

Theme application updates the application palette, tooltip palette, Qt color scheme and supported theme-dependent icons.

Custom Properties

The constants in npi::gui::Props identify dynamic properties used to request special widget behavior.

  • Use the Constant value when calling setProperty() in C++.
  • Use the String name as the dynamic property name in Qt Designer.
  • Use the specified Type for the property value.
  • Set boolean properties to true to enable their behavior.
Note
  • Prefer to set the property before the widget is polished.
  • If needed, polish the widget manually using its style, for example widget->style()->polish(widget).
  • Removing a property does not necessarily undo changes made during polishing.
Warning
Properties whose names begin with npi_gui_private_ are reserved for internal use in Gui.cpp.

Usage

Include Gui.h and the Qt headers required by each example. The examples assume an existing QApplication, an initialized GUI system, and an owning QWidget* parent where used.

Selecting a theme and obtaining colors

npi::gui::setTheme(npi::gui::Theme::Dark);
const npi::gui::Theme theme = npi::gui::theme();
const bool dark = npi::gui::isDarkBackground();
const QColor buttonBackground = npi::gui::surfaces().raised_;
const QColor lightEditorBackground = npi::gui::surfaces(false).sunken_;
const QPalette palette = npi::gui::palette();
const QColor textColor = palette.color(QPalette::Active, QPalette::Text);

Configuring a password line edit

Set properties immediately after construction, before the widget is polished.

auto* passwordEdit = new QLineEdit{parent};
passwordEdit->setProperty(npi::gui::Props::PasswordLineEdit_, true);

Assigning theme-dependent icons

Set an action's icon properties before adding it to a menu or toolbar.

auto* menu = new QMenu{parent};
auto* saveAction = new QAction{"Save", menu};
saveAction->setProperty(npi::gui::Props::IconName_, QString{"save"});
menu->addAction(saveAction);

For a checkable action, supply an On-state icon when needed.

auto* pauseAction = new QAction{"Pause", menu};
pauseAction->setCheckable(true);
pauseAction->setProperty(npi::gui::Props::IconName_, QString{"pause"});
pauseAction->setProperty(npi::gui::Props::IconOnName_, QString{"resume"});
menu->addAction(pauseAction);
Note
These examples require the corresponding icon resources. See Theme-Dependent Icons for resource naming and lookup.

Displaying a color

Set the property before polishing. Its color value can then be changed at runtime.

auto* colorDisplay = new QPushButton{parent};
colorDisplay->setProperty(npi::gui::Props::ButtonColorDisplay_, QColor{40, 120, 200});
// Later, after normal widget initialization:
colorDisplay->setProperty(npi::gui::Props::ButtonColorDisplay_, QColor{200, 80, 40, 128});
Note
  • Keep the button enabled to display the actual color; a disabled button shows it in grayscale.
  • The button still accepts mouse clicks. Leave its click signal unconnected when it is only intended as a display.

Creating an exclusive button group

Create the base and its immediate child buttons before polishing.

auto* modeGroup = new QWidget{parent};
modeGroup->setProperty(npi::gui::Props::ButtonGroupBase_, true);
auto* modeLayout = new QHBoxLayout{modeGroup};
modeLayout->setContentsMargins(0, 0, 0, 0);
modeLayout->setSpacing(0);
auto* modeA = new QPushButton{"Mode A", modeGroup};
auto* modeB = new QPushButton{"Mode B", modeGroup};
modeLayout->addWidget(modeA);
modeLayout->addWidget(modeB);
modeGroup->ensurePolished();
modeA->setChecked(true);

To use a sunken background, also set the following property before polishing:

modeGroup->setProperty(npi::gui::Props::SunkenBase_, true);
Note
Use npi::gui::Props::SunkenBase_ or npi::gui::Props::RaisedBase_ without npi::gui::Props::ButtonGroupBase_ when only a shared background is needed.

Configuring a widget inside an item view

Mark the root widget before installing it. Its descendants do not need their own ItemViewWidget property.

// The table must already contain cell (0, 0).
auto* cellWidget = new QWidget;
cellWidget->setProperty(npi::gui::Props::ItemViewWidget_, true);
auto* cellLayout = new QHBoxLayout{cellWidget};
cellLayout->setContentsMargins(0, 0, 0, 0);
auto* cellEdit = new QLineEdit{cellWidget};
cellLayout->addWidget(cellEdit);
table->setCellWidget(0, 0, cellWidget);
Note
The table takes ownership of the installed widget.

Changing properties after polishing

For properties that require setup, manually polish the widget after changing the property. If the change affects sizing, also request recalculation of its size hint.

// An existing QPushButton* button:
button->setProperty(npi::gui::Props::WidthSameAsHeight_, true);
button->style()->polish(button);
// Invalidate a cached size hint when immediate recalculation is needed.
QEvent styleChange{QEvent::StyleChange};
QCoreApplication::sendEvent(button, &styleChange);
button->updateGeometry();
button->update();
Note
Properties that support runtime updates, such as an initialized npi::gui::Props::ButtonColorDisplay_ color, do not require repeated polishing.
Warning
Manual polishing does not undo previous configuration. Prefer setting properties before the initial polish, especially those that create actions or configure widget groups.

Application Font

The GUI keeps the default application font provided by Qt and the operating system. It does not assign a custom application-wide font family. On Windows, this is normally a system UI font such as Segoe UI, but the implementation does not hard-code that family.

Why the default font is retained

Atkinson Hyperlegible and Atkinson Hyperlegible Next were evaluated as possible application fonts. Their distinction between similar characters, such as O and 0, or I, l, and 1, is useful for technical applications. However, testing showed several drawbacks:

  • The tested font files did not contain all required UI symbols. For example, the tested Atkinson Hyperlegible font lacked U+25CF (●), which was used for password masking.
  • The first password-symbol fallback under Qt 6.8 coincided with handled Bug: Font CacheOverflowException exceptions and a noticeable initial delay.
  • Their font metrics and perceived text size differed from Segoe UI at the same point size. Centered text could still appear vertically offset.
  • Changing the point size improved the perceived text size but did not eliminate the alignment differences.
  • Using these fonts throughout the GUI would require additional font-specific sizing and alignment adjustments.

Keeping the default font avoids those additional adjustments and preserves the platform's normal starting point for GUI sizing.

Note
These observations come from earlier font experiments in Qt 6.8.3. They do not establish that the same fallback issue occurs in the current Qt 6.12.0 version.

Sizing and accessibility

The style captures the application font and its sizing baseline during initialization. Control sizes are calculated using font metrics rather than assuming a particular font family.

Note
  • Windows accessibility text sizing can influence the initial application font supplied by Qt.
  • The GUI does not implement a complete runtime refresh of its sizing baseline when Windows font settings change. Restart the application after changing these settings.
  • Keeping the default font does not guarantee that every character is available without font fallback.

For content that benefits from fixed-width alignment or clearer character shapes, the bundled JetBrains Mono font can be assigned to individual widgets. See Technical Font.

Technical Font

JetBrains Mono is the bundled technical font, available in addition to the normal application font. Its monospaced design supports fixed-width alignment, while distinct shapes for characters such as 0 and O, or 1, l and I, make technical content easier to read accurately. See the JetBrains Mono design overview for examples of these character differences.

Use it selectively for content such as:

  • Identifiers, serial numbers and other values where confusing similar characters could cause mistakes.
  • Hexadecimal values, memory addresses and byte sequences.
  • Code, expressions and plain-text output that benefits from fixed-width alignment.

Font availability is managed by the GUI system:

  • During GUI initialization, the private util::initFont() function registers the bundled Regular, Bold, Italic and Bold-Italic files from :/fonts/ with Qt's application font database, before GuiStyle is constructed. A separate operating-system font installation is not required.
  • Registration makes the font available to the application; it does not replace the default application font or assign JetBrains Mono to widgets automatically.
  • The loading pass runs once. A failed font load produces a warning and is not retried on later initialization calls.

To use the font, copy the target widget's font, change its family to "JetBrains Mono", and assign it back to the widget. This preserves the existing font size instead of introducing a hard-coded technical-font size. Bold and italic can be requested through the usual QFont settings; use the same family name for all variants. See QFont for the font-selection API.

The following example assumes that QApplication exists, GUI initialization has completed as described in Initialization, and parent is the owning widget:

auto* lineEdit = new QLineEdit{parent};
QFont monoFont{lineEdit->font()};
monoFont.setFamily("JetBrains Mono");
lineEdit->setFont(monoFont);

The style compensates for JetBrains Mono's higher visual alignment by shifting text down by one pixel in several places:

  • GuiStyle::drawItemText() adjusts text drawn through that style function.
  • draw::adjustedText() applies the same correction in custom drawing paths, including button labels, combo-box text and header labels.
  • GuiStyle::subElementRect() adjusts the line-edit contents rectangle.
Note
  • The alignment corrections recognize "JetBrains Mono" in the font's requested family list. Use the family name exactly as shown in the example.
  • The affected drawing paths apply the correction automatically; do not add another vertical offset when using those paths.
  • These corrections do not change the font's metrics globally. Custom painting or text rendering that bypasses the listed paths must be checked separately for visual alignment.

Themes and Colors

Theme selection and effective background

The selected theme and the effective background are separate:

  • npi::gui::Theme::Dark always selects the application's dark appearance.
  • npi::gui::Theme::Light always selects the application's light appearance.
  • npi::gui::Theme::System, the initial selection, follows the Windows application-theme preference.
  • npi::gui::theme() returns the selection.
  • npi::gui::isDarkBackground() returns whether the effective background is dark.

For example, the selection can remain System while the effective background changes from light to dark.

System mode selects one of the application's own palettes. It does not copy the complete Windows theme or accent-color configuration.

Following the Windows theme

The system preference is read from AppsUseLightTheme under the current user's Windows personalization settings. A missing value defaults to light.

While System mode is selected, the native event filter rechecks this preference when it receives a WM_SETTINGCHANGE notification for ImmersiveColorSet. Explicit Dark and Light selections do not follow these notifications.

Note
Theme preference persistence is the caller's responsibility. The GUI system does not save the selection.

Applying a theme

The initial theme is always applied during GUI initialization. Afterwards, the appearance is refreshed only when the effective dark/light background changes.

Each refresh:

  • Sets the application palette.
  • Sets the tooltip palette.
  • Sets QStyleHints to the matching Dark or Light color scheme.
  • Updates registered theme-dependent action icons.
  • Updates theme-dependent button icons and label pixmaps.

Selecting Dark while System already resolves to dark changes the selection without refreshing the same appearance.

If another theme request occurs during an update, the current update finishes before the latest requested background is applied.

Note
Even in System mode, the Qt color scheme is explicitly set to Dark or Light. The GUI system follows Windows separately and keeps Qt's color scheme aligned with its own palette.

Using theme colors

Use the public surface and palette functions when custom content must match the GUI:

  • npi::gui::surfaces() returns the effective background's sunken, normal, and raised surface colors.
  • npi::gui::palette() returns the effective background's GUI palette, including text, highlight, and disabled colors.
  • Passing true to either function selects dark colors; passing false selects light colors without changing the configured theme.

These functions return copies. Changing a returned copy does not modify the GUI system.

Note
  • Returned colors do not update automatically. Custom widgets that cache them must refresh their colors and repaint when the application palette changes.
  • QPalette::Button and QPalette::Base intentionally use the same background colors as QPalette::Window. Use the raised and sunken surface colors for custom button and text-entry backgrounds.
  • palette() returns the GUI's stored theme palette, not any independently modified application or widget palette. Use the widget's own palette when painting should respect local palette overrides.

Native title bars

Native title bars are managed by Qt and Windows. The GUI system does not assign custom caption colors or draw title-bar controls. The matching Qt color scheme is requested when the application appearance changes. Native title-bar colors are not required to match the application's window background exactly.

Theme-Dependent Icons

An icon name is a resource basename without a path or extension. For an object whose npi::gui::Props::IconName_ property contains "save", lookup proceeds in this order:

  1. :/icons/dark/save.png or :/icons/light/save.png, according to the effective variant.
  2. :/icons/save.png if that theme-specific resource does not exist.

The opposite theme's directory is not searched. Supply Qt resources at these paths; the mechanism does not load arbitrary filesystem paths or operating-system theme icons.

For buttons and actions, QIcon::Off and QIcon::On states are resolved independently:

  • npi::gui::Props::IconName_ supplies the Off-state resource, and npi::gui::Props::IconOnName_ supplies the On-state resource. Providing an On-state icon does not itself make the button or action checkable.
  • The original icon is stored on the first dynamic-icon update. If a state's name is empty or its resource is unavailable, that state falls back to the stored original icon's available QIcon::Normal pixmaps.
  • If both names are empty, no dynamic-icon update is performed.
  • A non-empty name for which neither resource exists produces a warning.

A QLabel uses only npi::gui::Props::IconName_. Failed lookup leaves its existing pixmap unchanged, which may be the pixmap from the previous theme.

Note
The original-icon fallback copies available QIcon::Normal state pixmaps; it does not preserve every custom icon mode or icon-engine behavior.

During polishing, the style initializes:

  • Property-based icons on push buttons and tool buttons.
  • Property-based pixmaps on labels.
  • Dynamic icons on actions already associated with the widget.
  • The dynamic icon of a tool button's default action.

Actions added later to monitored menus, menu bars, toolbars and tool buttons are initialized through QEvent::ActionAdded.

Note
Set an action's icon properties before adding it to its host. An unattached QAction is not discovered merely because it has a QObject parent.

On effective theme changes, registered actions are updated, and existing buttons and labels are checked for property-based icons. The action registry is non-owning and removes entries when actions are destroyed. Resource names are intended to remain fixed after setup; switching theme changes which resource is used, not the property values.

For a tool button driven by a default action, normally put the dynamic-icon properties on the action so there is one source for its icon. The separate menu-drawing customization also recolors named edit-* icons to match enabled and disabled menu text; this is independent of resource-name lookup.

Grouped and Embedded Widgets

Grouped controls and embedded item-view widgets share background-suppression helpers but have different purposes:

  • npi::gui::Props::SunkenBase_ and npi::gui::Props::RaisedBase_ provide shared rounded backgrounds using npi::gui::Surfaces::sunken_ and npi::gui::Surfaces::raised_, respectively. Ordinary widget descendants have their backgrounds suppressed; explicitly marked sunken or raised bases retain their own surfaces.
  • npi::gui::Props::ButtonGroupBase_ additionally makes immediate QPushButton and QToolButton children checkable and places them in an exclusive QButtonGroup. An existing direct-child group is reused; otherwise one is created. Choose an initial checked button explicitly when required.
  • A standalone npi::gui::Props::ButtonGroupBase_ uses a raised background. When nested inside another group base, it shares the enclosing background unless an explicit surface property is enabled on the same widget. Its button grouping remains independent of any enclosing button group.
  • npi::gui::Props::SunkenBase_ takes precedence over npi::gui::Props::RaisedBase_. Item-view configuration takes precedence over all group-base background drawing.
  • A root marked with npi::gui::Props::ItemViewWidget_ and its widget descendants are configured for transparent backgrounds inside the owning view. QSizePolicy::Fixed vertical size policies are changed to QSizePolicy::Expanding so nested controls can fill their cell. Standard control-height and square-size adjustments are bypassed there.
Note
npi::gui::Props::SunkenBase_, npi::gui::Props::RaisedBase_ and npi::gui::Props::ButtonGroupBase_ leave layout contents margins and spacing unchanged. Configure them explicitly: use zero margins and spacing for tightly joined controls, or nonzero values for padding and separation within the shared background. A layout does not need to exist when the base is polished.

The style installs hierarchy filters so newly added widget descendants receive the appropriate configuration. QEvent::ChildAdded handling is deferred until events are processed because the notification can arrive during child construction; guarded pointers prevent access to objects deleted before the callback. The callback also checks that the child still belongs to the original host. For overlapping item-view and group configuration, item-view handling is applied first.

Mark only the root explicitly assigned to an item view. Do not mark the entire view, its viewport or temporary Qt-created delegate editors as application-supplied cell widgets. Selection highlighting is suppressed beneath an index widget whose root has npi::gui::Props::ItemViewWidget_, keeping embedded text readable.

Warning
These configurations are not reversible reparenting operations. Widgets may be added or removed, but a configured group or cell-widget hierarchy is not intended to be moved elsewhere and reused as an ordinary unconfigured hierarchy. Removing all group-base properties leaves previously configured descendants unchanged. If no enclosing group or item-view configuration applies, newly added descendants then remain ordinary widgets. Removing npi::gui::Props::ButtonGroupBase_ does not undo existing button grouping or checkability; manual polishing does not restore the original configuration.

Custom Drawing and Sizing

The custom style coordinates geometry and painting rather than treating each control independently. The main drawing responsibilities are:

  • Rounded button and text-entry backgrounds, pressed feedback, bottom focus indicators, translucent default-button overlays and grouped-control surfaces.
  • Push-button text/icon/menu layout, checkboxes, radio buttons, spin-box arrows and scrollbar controls.
  • Menu, combo-box popup and tooltip backgrounds using a npi::gui::Surfaces::raised_ fill with a npi::gui::Surfaces::sunken_ outline, plus menu-item highlights and selected item-view text backgrounds.
  • Tree-branch icons, compact splitter grips and progress-bar tracks. Progress fill drawing remains delegated to Fusion so orientation, inverted appearance and busy mode are retained.
  • Specialized table headers and completion-popup text, described in the following sections.
  • QFrame::HLine and QFrame::VLine are drawn as centered, one-unit separators using the theme's disabled text color. Each end is inset by six widget-coordinate units; the inset is omitted when the available length is 12 units or less.

The normal Fusion drawing is retained where no customization applies. Some elements are intentionally left unpainted to avoid duplicate backgrounds, frames or combo-box drawing. New drawing code must preserve the painter state when changing pens, brushes, transforms, clipping or render hints.

The standard height calculation uses the application font's attributes with the widget font's configured pixel or point size. This keeps controls aligned when a widget uses another family, such as JetBrains Mono, at the same size. The current calculation:

  • Normalizes the minimum height to at least 12 and the maximum to at least that minimum.
  • Adds 8 to the measured font height for borders and minimum icon-edge spacing, then takes the larger of that result and the normalized minimum height.
  • Rounds up to a heightQuantum of 4, then clamps to the maximum height. A restrictive maximum can therefore produce a height that is not a multiple of 4.
  • Derives icon dimensions from the resulting height, border width and height-dependent edge spacing.

These are Qt widget-coordinate dimensions, not a promise of a fixed number of physical display pixels. Standard heights apply to push buttons, tool buttons, line edits, combo boxes and spin boxes with a QSizePolicy::Fixed vertical size policy. Embedded item-view widgets, internal complex-control line edits and line-edit tool buttons retain Qt-controlled sizing.

Square sizing is automatic for menu-free icon-only push buttons and menu-free tool buttons displaying only an icon or arrow. npi::gui::Props::WidthSameAsHeight_ requests it explicitly for other applicable controls. It changes the size hint, not the layout's allocation, and minimum/maximum widths can prevent a square result.

Scrollbar thickness is shared between vertical scrollbar width and horizontal scrollbar height. It is calculated once during style construction from the application font's point size multiplied by 1.1, rounded and clamped to 10–32 widget-coordinate units. When no positive point size is available, it uses 10.

Other geometry adjustments include font-scaled tree indentation and indicator sizes, extra space and even heights for item-view items, compact menu items, and push-button widths that account for text, icons and menu arrows. Multiline push-button text adds a font-line height for each line after the first.

Note
The style caches application sizing data at construction and reuses it when the widget's configured font size and height limits permit. Qt widgets may also cache size hints. When a setup change does not invalidate that cache, a QEvent::StyleChange event can request recalculation; repainting alone does not recalculate layout geometry. See Usage.

Table and Tree Headers

The multi-level header renderer applies to QTableWidget, not arbitrary QTableView models. It reads normal model header text, including Qt's default labels when explicit header items are absent:

  • Horizontal labels use newline-separated levels, ordered top to bottom: "Input\nVoltage".
  • Vertical labels use the exact separator " > ", including its spaces, ordered left to right: "Group A > Channel 1".
  • Empty parts are ignored. Shorter hierarchies are aligned at the deepest level by prepending empty parent levels; blank separators cannot reserve a level.
  • The maximum depth is determined by non-hidden sections.

Equal labels merge across adjacent sections in non-hidden visual order only while all their parent levels also match. Moving or hiding sections therefore affects which labels are adjacent and can merge. Off-screen but non-hidden sections still participate in grouping.

For example, in a table with at least three columns:

table->setHorizontalHeaderLabels({
"Input\nVoltage", "Input\nCurrent", "Output\nVoltage"
});

The first two columns share the upper label Input. The third belongs to Output; its Voltage label does not merge with Voltage under Input. For a table with at least two rows, the analogous vertical format is:

table->setVerticalHeaderLabels({
"Group A > Channel 1", "Group A > Channel 2"
});

Selection and current-cell emphasis are computed separately, taking cell spans and hidden sections into account. A header group is marked when it contains the relevant non-hidden row or column span. Header-item enabled flags control disabled text appearance.

Note
A merged parent uses disabled text styling only when all its child sections are disabled. This controls appearance, not whether the header section accepts input.

The renderer paints the full header viewport once per full paint. A viewport event filter promotes partial paints to full updates so merged sections can be drawn together. Horizontal levels share the available height; vertical parent levels are positioned using text widths. Provide sufficient header height or width for the chosen hierarchy, especially after font or label changes.

These are visual groups, not merged QHeaderView interaction regions or model sections. Normal logical indices and header interactions remain separate. QTreeWidget uses a simpler header: it draws the current column's text in bold with a bottom line, without interpreting the table hierarchy separators.

Warning
The custom table and tree header paths do not draw standard header icons or sort arrows.

Completion Popups

Recognized QCompleter popup items emphasize the completion suffix:

  • A visible matching prefix is identified using the completer's case-sensitivity setting. Its displayed casing comes from the model's text, not from the user's typed prefix.
  • In ordinary, non-highlighted items, the prefix is dimmed while the suffix keeps the normal text color. Selected or hovered items use normal text coloring.
  • When space is limited, the suffix is prioritized by eliding or dropping the prefix first. If the suffix itself does not fit, it is right-elided. Exact completions with no suffix are right-elided normally.
  • Items without a visible matching prefix use normal text coloring.

The helper retains the base style's non-text item drawing and lays out the customized text within the intersection of the text rectangle and the painter's existing clip. It changes presentation only; completion matching, filtering and insertion remain QCompleter's responsibility.

Note
Recognition requires the completion model to be owned by its QCompleter and the widget passed to the style to be that completer's popup. Custom delegates, proxy arrangements or popup implementations that bypass this path may retain ordinary item drawing.

Limitations

  • The current implementation is Windows-specific and requires Qt Widgets and the Fusion style. It does not provide a Qt Quick style or a portable native-theme abstraction.
  • Native caption-color customization requires Windows support for DWMWA_CAPTION_COLOR, documented from Windows 11 build 22000. If the caption-color request fails, a warning is logged; the GUI's custom widget painting remains in use. See Microsoft's DWM attribute documentation.
  • Perform GUI setup and widget changes on the GUI thread, following Qt's GUI-thread requirements. This module does not provide synchronization or cross-thread dispatch for its public functions.
  • Keep one GuiStyle installed for the application's normal lifetime. Replacing the application style is not a supported reset procedure: private widget markers and installed configuration are not designed as a reversible teardown/rebuild interface.
  • Runtime application-wide font changes are not supported by the sizing-cache design. In particular, changing Windows text-size settings is not handled as a complete font-and-layout refresh; restart the application to establish a new consistent baseline.
  • Custom palettes, style sheets and delegates can override or bypass parts of the centralized appearance. Neither a palette change nor an arbitrary custom widget guarantees that every surface follows the GUI's dedicated colors.
  • Property initialization may overwrite existing widget configuration. Observe the per-property restrictions, do not use internal properties, and do not repurpose configured group or item-view descendants as ordinary widgets.
  • npi::gui::Props::PasswordLineEdit_ provides password-entry presentation and visibility controls, not a password-validation policy. Configure any required validator and maximum length separately, and validate submitted values in application code.
  • The custom header renderer is specific to QTableWidget and QTreeWidget. Visual header groups do not implement group-level sorting or resizing, and header icons/sort arrows are not drawn by these paths. Full-viewport header painting also warrants performance checks for large tables.
  • Font-specific optical correction is deliberately limited to the paths described in Technical Font. Other families, custom text painting and unusual font sizes require visual verification.
  • Integration with Qt internals must be rechecked on Qt upgrades, particularly internal line-edit naming, the clear-action object name, combo-box popup behavior and completion-model ownership assumptions.

Diagnostics and Maintenance

The GUI implementation logs lifecycle and theme activity, and warns when optional customization cannot be applied. Useful cases to check include:

  • Missing theme-dependent icon resources: check the basename and Qt resource aliases for both theme variants and the common fallback.
  • Bundled font-load failures: check the four JetBrains Mono resources. The loading pass is not retried automatically.
  • Missing line-edit clear actions: the lookup depends on Qt's internal object and class names, and the customization attempt is recorded even when it fails.
  • Native caption-color failures: the warning includes the widget name and HRESULT for platform diagnosis.

When changing the style or upgrading Qt, check:

  • Both themes and live system-theme switching.
  • Enabled, disabled, focused, pressed and checked controls.
  • Normal and technical fonts, display scaling and larger text.
  • Grouped and embedded widgets, including dynamically added children.
  • Table headers with hidden or moved sections and cells spanning multiple rows or columns.
  • Completion popups with exact matches, case-insensitive matches and narrow widths.

Keep Gui.h, implementation comments, examples and this page consistent. The historical font investigation below records a separate experiment and should not be treated as a list of initialization steps currently performed by Gui.cpp.

Bug: Font CacheOverflowException

Bug
GUI System : Font CacheOverflowException DirectWrite fallback path

Note
This section records the earlier Atkinson application-font experiment. The current Gui.cpp does not select Atkinson, warm up font fallback or override the password-mask character. The examples below are optional experimental workarounds, not part of the normal initialization sequence.

While trying to use Atkinson Hyperlegible as the application font, I noticed that if a password line edit had its echo mode set to QLineEdit::Password and a character was entered, or if characters had already been entered and the line edit's echo mode was changed from QLineEdit::Normal to QLineEdit::Password, exactly 4 exceptions were shown in the debugger output. Afterwards, everything worked normally and no further exceptions were thrown.

Qt 6.8 changed the default Windows font backend from GDI to DirectWrite, as documented in What's New in Qt 6.8. In the tested configuration, rendering a character missing from the primary font for the first time produced the following debugger output:

Exception thrown at 0x00007FF99B4F187A in E118_Main.exe: Microsoft C++ exception: CacheOverflowException at memory location 0x00000099324F2CC0.
Exception thrown at 0x00007FF99B4F187A in E118_Main.exe: Microsoft C++ exception: CacheOverflowException at memory location 0x00000099324F2CC0.
Exception thrown at 0x00007FF99B4F187A in E118_Main.exe: Microsoft C++ exception: CacheOverflowException at memory location 0x00000099324F2CC0.
Exception thrown at 0x00007FF99B4F187A in E118_Main.exe: Microsoft C++ exception: CacheOverflowException at memory location 0x00000099324F2CC0.

The observations in that test were:

  • The exception type is CacheOverflowException.
  • Four exceptions appeared on the first fallback lookup.
  • The application continued normally afterward, without an unhandled exception or observed failure.
  • Subsequent missing-character rendering did not reproduce the exceptions during that run.

The count and timing are observations, not guarantees across Qt, Windows or font versions. In the same experiment, forcing the older GDI backend avoided the exceptions:

int main(int argc, char* argv[])
{
qputenv("QT_QPA_PLATFORM", "windows:fontengine=gdi");
QApplication app{argc, argv};
// ...
}

This behavior is consistent with initialization or caching in the DirectWrite fallback path, but the debugger messages alone do not establish the exact internal cause. The important practical result was a one-time delay followed by normal rendering in the tested run.

Note
The GDI backend is a legacy alternative. Do not switch the whole application's font backend solely to silence handled debugger exceptions without also evaluating rendering and font-feature differences.

One possible mitigation for a reproducible first-use delay is to trigger the relevant fallback during startup, before the main UI is shown. This moves the work earlier; it does not fix the backend or guarantee that every later fallback path is warmed. The following experiment renders a character known to be missing from the tested primary font:

void warmUpFontFallback()
{
QImage image{32, 32, QImage::Format_ARGB32_Premultiplied};
image.fill(Qt::transparent);
QPainter painter{&image};
painter.setFont(qApp->font());
// U+25CF BLACK CIRCLE is missing from the tested Atkinson font.
painter.drawText(image.rect(), Qt::AlignCenter, QString{QChar{0x25CF}});
}

If repeating the Atkinson experiment, construct QApplication, register the Atkinson font and perform the application-font setup before triggering GUI-style initialization through QCoreApplication::processEvents() or a public theme query such as npi::gui::theme(). Qt 6.8 introduced application-defined fallback families; the optional Segoe UI preference below still requires that font to be available:

// Add Segoe UI as an explicit fallback font.
// This is optional and makes Segoe UI preferred for missing Common/Latin glyphs.
QFontDatabase::addApplicationFallbackFontFamily(
QChar::Script_Common,
"Segoe UI");
// Set the application font.
// Make sure Atkinson Hyperlegible has already been added to the font database.
QFont appFont{qApp->font()};
appFont.setFamily("Atkinson Hyperlegible");
appFont.setPointSize(10);
qApp->setFont(appFont);
// Trigger the relevant font fallback before showing the UI.
warmUpFontFallback();
// Continue with the rest of the application initialization.

A separate experiment can avoid this particular missing glyph by selecting a password-mask character present in the chosen font. The following possible styleHint() override is not implemented in the current GuiStyle:

int styleHint(
QStyle::StyleHint hint,
const QStyleOption* option = nullptr,
const QWidget* widget = nullptr,
QStyleHintReturn* returnData = nullptr) const override
{
switch(hint) {
case SH_LineEdit_PasswordCharacter:
return 0x2022; // • instead of the default U+25CF ● BLACK CIRCLE
default:
break;
}
return QProxyStyle::styleHint(hint, option, widget, returnData);
}

In the tested Atkinson font, U+2022 (•, BULLET) was available while U+25CF (●, BLACK CIRCLE) was not. Choosing U+2022 avoided fallback for that masking glyph; it did not eliminate the possibility of fallback for other characters. Recheck glyph coverage and behavior before applying either workaround to another font or runtime version.
