Project Setup

This page defines the general project structure and development standards used across projects. It includes information about directory layout, file placement, naming conventions, coding conventions, documentation style, and other project-level practices that are independent of any specific IDE.

Rules

REQUIRED
Project Setup: Rules

  1. Structure
    • Only entry files, such as main.cpp, are placed at the project root.
    • Manually created project files are placed inside project-relative subfolders.
    • Each project uses the following directories, created only when required:
      • <Project>\ext\ : Header and source files obtained from external sources.
      • <Project>\img\ : Image files, such as .png, .jpg, .svg, etc.
      • <Project>\ico\ : Icon files, such as .ico.
      • <Project>\res\ : Resource files, such as .rc, .qrc, etc.
  2. Includes
    • All project-specific includes use a project-relative subpath, such as #include "abc/def.h".
    • DO NOT use parent-relative includes, such as #include "../abc/def.h".
  3. Coding
    • NO global functions or variables, except required entry points and external API callbacks.
    • NO simple/common names such as Font, Show, etc. for classes/structs.
    • Member variables/functions end with an underscore _.
    • Static member variables/functions start with a capital letter.
  4. Comments
    • ASCII-only.
    • NO Doxygen comments inside function bodies.

Recommendations

  1. Structure
    • The Project name and Solution name should be different.
    • Main project inside a Visual Studio solution should be named App.
    • Non-main projects inside a Visual Studio solution can be named as required.
    • Suggested directories for splitting header, source and form files, if desired:
      • <Project>\hdr\ : Project header files, such as .h, .hpp, etc.
      • <Project>\src\ : Project source files, such as .c, .cpp, etc.
      • <Project>\gui\ : Qt form files, such as .ui.
  2. Includes
    • Keep includes minimal.
    • Prefer forward declarations in headers when practical.
  3. Coding
    • Use #pragma once in headers.
    • Start signal names with sig_.
    • Start slot names with on_ or on.
  4. Comments
    • Use /** ... */ style for high-level declarations, such as files, namespaces, classes, structs, etc.
    • Use /// above functions.
    • Use ///< for trailing single-line Doxygen comments after declarations.

VS Project Settings

This section applies only to projects developed with Visual Studio. Ignore this section for projects that use a different build system or IDE.

Set Project Properties > Configuration: All Configurations and Platform: All Platforms (if possible) first.

Project Properties > Configuration Properties:
(Auto = Automatically assigned by VS Property Sheets if it is set up)

  • General
    • Output Directory: F:\Misc\VS_Bins\$(SolutionName)\$(Platform)_$(Configuration)\ Auto
    • Intermediate Directory: F:\Misc\VS_Objs\$(SolutionName)\$(Platform)_$(Configuration)__$(ProjectName)\ Auto
    • C++ Language Standard: ISO C++20 Standard (/std:c++20) Auto
    • C Language Standard: ISO C17 (2018) Standard (/std:c17) Auto
  • C/C++
    • Preprocessor
      • Preprocessor Definitions: QT_MESSAGELOGCONTEXT;%(PreprocessorDefinitions) Auto
  • Linker
    • System
      • SubSystem: Windows (/SUBSYSTEM:WINDOWS)
Note
Instead of $(SolutionName), Visual Studio may show $(_SolName). This is a custom macro generated by VS Property Sheets and appears when the property is assigned from that property sheet. In normal solution builds, $(_SolName) resolves to the solution name. If no solution name is available, the property sheet may use a fallback value.

Descriptions:

  • Output Directory

    This directory contains the final build outputs (for example: .exe, .dll, .pdb, .lib). It is recommended that projects inside a single solution share the same output directory, as long as output file names do not collide, to facilitate interaction between projects. Default is $(SolutionDir)$(Platform)\$(Configuration)\ (e.g. ...\MySolution\x64\Debug\).

    • Safe to delete, Visual Studio/MSBuild recreates it when needed.
    • In a .props XML file, this property is named OutDir.
    • If changed, the previously generated folder is not removed automatically.

  • Intermediate Directory

    This directory contains intermediate build artifacts (for example: .obj, .pch, moc_*.cpp, ui_*.h, qrc_*.cpp, generated .tlog, etc.). It is highly recommended that each project has a different intermediate directory, even inside the same solution, to avoid name collisions. Default is $(ProjectDir)$(Platform)\$(Configuration)\ (e.g. ...\MyProject\x64\Debug\).

    • Safe to delete, Visual Studio/MSBuild recreates it when needed.
    • In a .props XML file, this property is named IntDir.
    • If changed, the previously generated folder is not removed automatically.

  • C++ Language Standard:

    The same value is also found at Project Properties > Configuration Properties > C/C++ > Language > C++ Language Standard, changing one is sufficient, the change is reflected in other location as well.

  • C Language Standard:

    The same value is also found at Project Properties > Configuration Properties > C/C++ > Language > C Language Standard, changing one is sufficient, the change is reflected in other location as well.

  • Preprocessor Definitions: QT_MESSAGELOGCONTEXT;%(PreprocessorDefinitions)

    Qt's log context fields (category, file, function, line) are not available in Release build, with QT_MESSAGELOGCONTEXT macro these are enabled in Release builds as well.

  • SubSystem: Windows (/SUBSYSTEM:WINDOWS)

    GUI applications should use Windows subsystem; console tools should use Console subsystem. Some templates (including "Qt Empty Project") may default to Console subsystem, that's why this change is necessary. This setting can be changed through VS Property Sheets but it is later overridden by templates back to a hardcoded value. For this reason, setting SubSystem through VS Property Sheets is not useful.

VS Property Sheets

Visual Studio C++ projects can auto-import a per-user property sheet if it exists here:

%LOCALAPPDATA%\Microsoft\MSBuild\v4.0\

Visual Studio expects exact file names:

  • x64 Platform:
    Microsoft.Cpp.x64.user.props
  • Win32 Platform:
    Microsoft.Cpp.Win32.user.props

We can place our own .props file in the given location (create the directory if it does not exist) and rename the .props file to what Visual Studio expects. Same .props file content can be used for both Microsoft.Cpp.x64.user.props and Microsoft.Cpp.Win32.user.props if desired. These will then apply to any .vcxproj loaded/built via MSBuild under this Windows user account (Visual Studio builds, command line msbuild, CI jobs, scripts, etc.).

To avoid affecting unrelated projects, our .props file code includes a safeguard. The defaults properties are applied only when the project is located under approved roots on F:\ (any depth):

  • F:\Test\...
  • F:\Eval\...
  • F:\Demo\...
  • F:\Core\...
  • F:\Uniq\...
  • F:\Gear\...

Below is the complete code for the .props file:

<?xml version="1.0" encoding="utf-8"?>
<Project>
<!--
Microsoft.Cpp.<Platform>.user.props (per-user, per-platform)
This file is automatically imported (if it exists) by typical Visual Studio
C++ MSBuild projects (.vcxproj) when building the matching Platform:
- Microsoft.Cpp.x64.user.props -> applies when $(Platform) == x64
- Microsoft.Cpp.Win32.user.props -> applies when $(Platform) == Win32
Important behavior:
- This affects any build that loads/builds a .vcxproj via MSBuild
(Visual Studio IDE build, msbuild.exe, CI jobs, scripts, etc.).
- It does NOT affect build systems that do not use .vcxproj/MSBuild
(e.g., Ninja, Make, custom direct cl.exe invocations).
- It applies to both Debug and Release (and any other configurations)
unless you add additional conditions on $(Configuration).
Goal here:
- Apply a consistent OutDir/IntDir + language standards + a couple of
compile/link defaults
- ONLY for projects whose .vcxproj is located under specific "allowed"
roots on the F: drive:
F:\Test\...
F:\Eval\...
F:\Demo\...
F:\Core\...
F:\Uniq\...
F:\Gear\...
Notes on MSBuild concepts used below:
- PropertyGroup:
Defines MSBuild properties like OutDir and IntDir.
- ItemDefinitionGroup:
Defines default metadata for item types like ClCompile and Link.
This is the correct place for compiler/linker settings.
-->
<PropertyGroup>
<!--
$(MSBuildProjectDirectory) is the directory that contains the .vcxproj.
We append a trailing backslash to make prefix matching unambiguous and
robust. Example:
$(MSBuildProjectDirectory) = F:\Eval\MySol\MyProj
_ProjDirWithSlash = F:\Eval\MySol\MyProj\
-->
<_ProjDirWithSlash>$(MSBuildProjectDirectory)\</_ProjDirWithSlash>
<!--
_ApplyUserProps is our single "gate" switch.
It becomes "true" only if the project directory begins with one of our
approved roots. The trailing backslash in each root matters:
- F:\Test\ matches F:\Test\Anything\...
- F:\Test2\ does NOT match (avoids accidental partial matches)
OrdinalIgnoreCase ensures case-insensitive matching (F:\eval\... also matches).
-->
<_ApplyUserProps Condition="
$([System.String]::Copy('$(_ProjDirWithSlash)').StartsWith('F:\Test\', System.StringComparison.OrdinalIgnoreCase))
OR $([System.String]::Copy('$(_ProjDirWithSlash)').StartsWith('F:\Eval\', System.StringComparison.OrdinalIgnoreCase))
OR $([System.String]::Copy('$(_ProjDirWithSlash)').StartsWith('F:\Demo\', System.StringComparison.OrdinalIgnoreCase))
OR $([System.String]::Copy('$(_ProjDirWithSlash)').StartsWith('F:\Core\', System.StringComparison.OrdinalIgnoreCase))
OR $([System.String]::Copy('$(_ProjDirWithSlash)').StartsWith('F:\Uniq\', System.StringComparison.OrdinalIgnoreCase))
OR $([System.String]::Copy('$(_ProjDirWithSlash)').StartsWith('F:\Gear\', System.StringComparison.OrdinalIgnoreCase))
">true</_ApplyUserProps>
<!--
$(SolutionName) is often set when building via a .sln.
However, if you build a .vcxproj directly (or from some tooling),
$(SolutionName) can be empty. To avoid generating a path with a missing
segment, we create a stable fallback name.
This is only computed when _ApplyUserProps is true, because otherwise
we are not going to use it.
-->
<_SolName Condition="'$(_ApplyUserProps)'=='true' AND '$(SolutionName)' != ''">$(SolutionName)</_SolName>
<_SolName Condition="'$(_ApplyUserProps)'=='true' AND '$(SolutionName)' == ''">NoSolution</_SolName>
</PropertyGroup>
<!--
Build output/intermediate directories.
These are MSBuild properties (not compiler/linker flags), so they belong
in a PropertyGroup.
Important:
- Both OutDir and IntDir should end with a trailing backslash.
- These will apply to all configurations (Debug/Release/...) for the
current platform (x64 or Win32), as long as _ApplyUserProps is true.
Rationale:
- Prevents creation of local per-project folders like ".\x64\Debug\..."
(as long as this is in place BEFORE the first build of a project).
- Centralizes build artifacts so solution trees stay clean.
-->
<PropertyGroup Condition="'$(_ApplyUserProps)'=='true'">
<OutDir>F:\Misc\VS_Bins\$(_SolName)\$(Platform)_$(Configuration)\</OutDir>
<IntDir>F:\Misc\VS_Objs\$(_SolName)\$(Platform)_$(Configuration)__$(ProjectName)\</IntDir>
</PropertyGroup>
<!--
Default compiler and linker settings.
These are item metadata defaults, so they belong under ItemDefinitionGroup.
ClCompile:
- LanguageStandard: selects /std:c++20
- LanguageStandard_C: selects /std:c17
- PreprocessorDefinitions:
Adds QT_MESSAGELOGCONTEXT, then preserves existing defines via
%(PreprocessorDefinitions).
-->
<ItemDefinitionGroup Condition="'$(_ApplyUserProps)'=='true'">
<ClCompile>
<LanguageStandard>stdcpp20</LanguageStandard>
<LanguageStandard_C>stdc17</LanguageStandard_C>
<PreprocessorDefinitions>QT_MESSAGELOGCONTEXT;%(PreprocessorDefinitions)</PreprocessorDefinitions>
</ClCompile>
</ItemDefinitionGroup>
<!--
If you ever want to restrict to only Debug or only Release, add to the
Condition, for example:
Condition="'$(_ApplyUserProps)'=='true' AND '$(Configuration)'=='Debug'"
If you ever want to apply different values for x64 vs Win32, you can:
- keep two files (x64 and Win32) with different values, OR
- branch on $(Platform) inside the same file (not recommended here
because you are duplicating the same file anyway).
-->
</Project>
