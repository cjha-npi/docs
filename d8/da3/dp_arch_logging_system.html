Logging System

Overview

The logging system replaces Qt's default message handler and provides asynchronous file logging, optional console or debugger display, important-log forwarding, runtime configuration, persistent settings, directory cleanup, and best-effort fatal and crash reporting. Normal messages are written to a process-specific *.log file. Crash, fatal and late messages are forwarded to a separate helper process that maintains a corresponding *.imp.log file. Critical messages, and warning messages when configured as important, are also forwarded to the helper while remaining available in the normal *.log file.

The implementation is designed to keep ordinary logging work away from application threads. The Qt message handler captures the message metadata, assigns sequence and timing information, obtains context-cache slots and enqueues a compact log record. Formatting, normal file output, display routing, rate limiting, and warning-to-important forwarding are performed by worker threads.

Implementation

Primary components:

  • Qt message handler: Captures each message and creates a OneLog record.
  • File worker: Owns normal log formatting and file output and is the only producer of the display queue.
  • Display worker: Formats selected fields for a console or debugger and applies display rate limiting.
  • Important-log bridge: Sends important records through an anonymous pipe to npiImpLog.exe.
  • Context caches: Store normalized category, file/line, and function text and place compact indices in each log record.
  • Configuration layer: Loads, validates, applies, and optionally persists logging settings.
  • Crash layer: Installs fatal and crash handlers that use pre-allocated buffers and restricted operations.

Normal message flow:

Qt logging call
-> message handler
-> file queue
-> file worker
-> normal *.log file
-> display queue, when display is enabled
-> display worker
-> Windows console or debugger

Important message flow:

Critical message
-> important-log bridge immediately
-> file queue for normal logging
Warning message, when Warn Is Important is enabled
-> file queue
-> file worker
-> important-log bridge
Fatal or crash message
-> crash-safe formatting path
-> important-log bridge
-> popup/debug output as applicable
-> process termination

Initialization

Initialization is registered through Q_CONSTRUCTOR_FUNCTION, so the logging system is prepared before normal application startup. It performs the following operations once:

  1. Installs the crash and fatal handlers.
  2. Installs the Qt message handler.
  3. Installs a logging-category filter while retaining the previous filter.
  4. Loads and normalizes the persistent configuration.
  5. Applies category filter rules and packed field layouts.
  6. Starts asynchronous directory cleanup.
  7. Starts the display worker when a console or debugger is available.
  8. Creates the initial log file paths, starts npiImpLog.exe, and starts the file worker.
  9. Registers process shutdown through std::atexit.

Failure to establish required normal logging support is considered fatal because continuing without a functional application log would make later failures difficult to diagnose.

Log Records and Context Caches

Each message is represented internally by a fixed-size OneLog record containing the level, context-cache indices, thread information, sequence number, application and thread timing, timestamp, thread delta, and message text. The structure is deliberately arranged and checked to remain 64 bytes on the supported build configuration.

The message handler always captures category, file/line, and function context. Three fixed-capacity caches normalize and store the text:

  • CategoryCache stores the logging category.
  • FileLineCache stores the shortened file path and line number.
  • FunctionCache stores the normalized function name.

Cache keys are derived from the referenced text rather than from pointer addresses. The character pointers stored in QMessageLogContext may remain unchanged while the text at those addresses changes, so pointer-based keys could incorrectly reuse previously cached values. Each cache publishes completed entries through atomic state changes and stores the normalized text in a fixed pool. If a cache or pool is exhausted, the corresponding field falls back to an empty or unknown value rather than destabilizing logging.

Log Fields and Formatting

Field layouts are normalized from case-insensitive, space-separated field names. Invalid names and duplicates are removed while the order of valid fields is preserved. The normalized layout is packed into a 64-bit atomic value, so workers can refresh the active layout without sharing Qt containers across their processing loops.

Available fields are:

  • DateTime : Local wall-clock date and time.
  • Sequence : Wrapping 32-bit log sequence number.
  • Level : Log message level from Debug to Fatal.
  • ThreadIndex : Monotonically assigned thread index; the main thread uses 1, and 0 means unassigned.
  • ThreadId : Windows thread ID obtained using ::GetCurrentThreadId().
  • AppTime : Elapsed time since logging-system initialization, formatted as hhh:mm:ss.zzz where zzz is milliseconds.
  • ThreadTime : Elapsed time since the thread first logged, formatted as hhh:mm:ss.zzz where zzz is milliseconds.
  • ThreadDelta : Time delta since the previous record emitted by the same thread, formatted using an adaptive unit.
  • Category : Logging category.
  • FileLine : File and line information.
  • Function : Function name.

The default normal-file layout is:

DateTime Sequence Level ThreadId AppTime Category Function

The default display layout is:

Level ThreadIndex ThreadDelta

The message is always appended after the configured fields and is separated by | . Text is sanitized so that each record remains on one physical line. Repeated whitespace is collapsed, | within supplied text is replaced with /, and unsupported characters are replaced with ?. File and display formatting use fixed-capacity buffers; an oversized field or message is truncated rather than dynamically expanding an internal formatting buffer.

Normal Log Files

Each directory activation creates a new base name using the local date and time followed by the process identifier:

yyyyMMdd_HHmmsszzz_PXXXXXXXX

XXXXXXXX is the uppercase, zero-padded, eight-digit hexadecimal process identifier. The normal log uses the .log extension and the important log uses the .imp.log extension.

The file worker opens the current normal log with exclusive write ownership. Other processes may read the file while it is active, but moving or deleting it is prevented by the open handle. A successful directory transition starts the important-log helper for the new path, switches the file worker to a new normal log, waits until that file is ready, updates the public base name, and then starts cleanup for the selected directory.

Important, Fatal, and Crash Logging

npiImpLog.exe is launched as a child process and receives important records through its standard input. Its standard output and standard error are redirected to NUL, and handle inheritance is restricted to the pipe read handle and the NUL handle. The parent retains the process handle and pipe write handle.

Critical messages are sent to the important-log bridge immediately and are also queued for normal file logging. Warning messages are forwarded to the important log by the file worker when the Warn Is Important setting is enabled. The helper creates the important file lazily when the first important record arrives. This is intentional: the presence of *.imp.log file is itself an indication that an important event occurred.

For concurrent fatal logging, only the first thread to claim fatal ownership writes the fatal record and displays the fatal popup. Other fatal threads give the owning thread a fixed grace period to report the failure and show a popup, then fail fast. A re-entrant fatal on the owning thread fails fast immediately rather than waiting on itself.

Crash and fatal paths use pre-allocated text buffers, lock-free atomic state, Windows interlocked operations, and restricted best-effort output. Crash handling cannot guarantee recovery or complete output after arbitrary process corruption; its purpose is to preserve the most useful failure information without creating additional dependencies on the normal workers.

Worker Threads and Queue Ownership

The file worker consumes the file queue, formats normal records in batches, writes them to the active file, optionally forwards warning records to the important-log bridge, and forwards displayable records to the display queue. Outside the internal test code, it is the only producer of the display queue.

The display worker consumes the display queue and writes formatted batches to the attached console or debugger. It can stop when neither output target is available. It is restarted directly when a temporary console is opened and by the file worker when a debugger is attached. Muting display output disables forwarding without affecting normal or important file logging.

Workers use an atomic wake-up flag together with wait() and notify_one(). Short idle sleeps allow bursts to be collected before a worker blocks. During shutdown, each worker performs additional empty-queue checks which give records already in transit time to be drained before the thread exits.

The display path limits output to 4096 lines per second. Excess records remain written to the normal log but may be suppressed from the console or debugger, with a summary reporting the number of suppressed display lines.

Console and Debugger Output

A console attached when the logging state is created is treated as permanent. The implementation opens CONOUT$ directly so console output remains independent of redirected standard output or standard error handles. Console input modes are adjusted to disable Quick Edit, insert mode, and mouse input because text selection can block WriteConsoleA or WriteConsoleW.

When no permanent console exists, a temporary console can be opened and closed through the public API. Closing a temporary console wakes the display worker so it can re-evaluate its output target and exit when no debugger is attached. Attaching or detaching a debugger is detected periodically by the file worker, which starts, stops, or wakes display processing as needed.

Colored output applies only to the Windows console. Debugger output and file output remain uncolored. Display muting is runtime-only and does not change persistent settings.

Configuration and Persistence

Persistent settings are stored in log_config.ini under the application program-data directory. Cross-process locking protects reads, writes, removals, and normalization of the settings file. Stored values equal to their defaults are removed rather than retained, keeping the file limited to actual overrides.

The following settings can be persisted:

  • Log directory
  • Maximum folder size
  • Normal-file fields
  • Display fields
  • Category filter rules
  • Warning-as-important state
  • Warning display state
  • Information display state
  • Debug display state
  • Colored-console state

Temporary mode applies subsequent configuration changes only to the current process. It does not automatically revert existing runtime values and does not itself save them when temporary mode is later disabled. Reapplying an unchanged value in persistent mode can therefore promote a temporary runtime value into persistent storage or remove an obsolete stored override.

Maximum-folder-size cleanup and persistence use separate single-shot debounce timers. Runtime configuration changes immediately, cleanup runs after the value settles, and persistent saving is separately delayed. This avoids repeated file system work when the value is connected directly to a QSpinBox::valueChanged signal. An active pending save is flushed during aboutToQuit.

Directory Validation and Switching

An empty directory argument is rejected. Non-empty paths are trimmed, normalized, created when necessary, checked for directory status, and tested for write access using a temporary file. To restore the default directory a separate npi::log::resetDirectory() function is provided.

On Windows, accepted paths must be drive-letter absolute paths such as C:\Logs or mapped-drive paths such as Z:\Logs. Relative paths, drive-relative paths such as C:Logs, malformed prefixes, and UNC paths are rejected because the important-log helper expects the same drive-letter path contract.

Directory changes are serialized by a dedicated mutex because switching the helper process, file-worker path, runtime configuration, cleanup request, and persistent setting forms one transaction. Selecting the already-active directory does not restart workers or display an information dialog; it only performs any required persistence promotion or stored-setting removal.

Maximum Folder Size and Cleanup

A maximum size of zero means unlimited storage and disables deletion. Otherwise, cleanup considers only normal application files whose names match:

xxxxxxxx_xxxxxxxxx_Phhhhhhhh.log

Here, x is a decimal digit and h is an uppercase hexadecimal digit. Important *.imp.log files, unrelated files, directories, and symbolic links are excluded.

Cleanup runs asynchronously on startup, after a successful directory transition, after a debounced maximum-size change, and when explicitly requested internally. A monotonically increasing cleanup sequence makes obsolete requests exit early, and a cross-process lock prevents multiple application instances from cleaning the same directory concurrently. Matching files are ordered oldest first, and removal is attempted until their combined size reaches the configured cleanup target.

Category Filtering

The implementation installs a category filter that records every encountered category name and then invokes the previously installed filter, when one exists. The public API can return all encountered categories or divide them into Qt categories, whose names begin with qt., and non-Qt categories.

Built-in filter rules differ between debug and release builds. User rules are normalized by removing whitespace and accepting only entries containing one key, one =, and a Boolean value of true or false. The normalized user rules are appended to the built-in rules and applied through QLoggingCategory::setFilterRules().

Shutdown

Process shutdown first enables shutdown mode so messages emitted after normal worker processing begins to stop are routed directly to the important-log bridge and, when attached, the debugger. Worker shutdown is performed once.

The file worker is requested to stop and joined before the display worker. This ordering is required because the file worker is the sole display-queue producer and may also restart the display worker during normal operation. After the file worker has completed its final drain, no new display records can be produced, so the display worker can drain its remaining queue and exit deterministically.

A console write can remain blocked while text is selected. Shutdown therefore waits a limited time for the display worker and then asks whether to continue terminating without waiting or to wait for the blocked write to return. The logging state is deliberately leaked, so continuing process termination does not invoke a std::jthread destructor that would otherwise wait for the blocked display thread.

Thread Safety and Usage Rules

The message handler, worker queues, context caches, display muting, temporary-mode state, and synchronized query functions support concurrent use. Crash-path atomic types are statically required to be lock-free.

Public configuration-changing functions are intended to be called from the GUI thread. Their stored values are protected against data races, but unrelated setters are not combined into one global configuration transaction. Directory transitions are explicitly serialized because they update multiple dependent resources. Timer creation and restart are marshalled to the Qt application thread when necessary.

Design Limits

The implementation intentionally accepts the following limits:

  • The 32-bit sequence number wraps after 4,294,967,296 assigned records.
  • Elapsed-time fields saturate at 999:59:59.999.
  • Context caches and their text pools have fixed capacities and are never reclaimed during the process lifetime.
  • Display output is rate-limited and may suppress lines that remain available in the normal log.
  • Display forwarding has a soft queue-backlog limit, if reached, file worker writes a log describing the skipped batch.
  • Maximum folder size is enforced at defined cleanup points rather than continuously after every file write.
  • Important, fatal, and crash output is best-effort when the process or operating environment is already failing.
  • UNC log directories are not supported.

Public API

The public API is declared in Log.h under npi::log and is organized into the following groups:

  • Temporary mode: npi::log::tempMode and npi::log::setTempMode.
  • Directory and file identity: npi::log::directory, npi::log::defaultDirectory, npi::log::setDirectory, npi::log::resetDirectory, and npi::log::fileBaseName.
  • Folder size: npi::log::maxFolderSizeMib, npi::log::setMaxFolderSizeMib, and npi::log::resetMaxFolderSizeMib.
  • Field layouts: npi::log::allFields, file-field functions, and display-field functions.
  • Categories and filters: base rules, custom rules, and encountered-category query functions.
  • Important and display settings: warning importance, per-level display toggles, console colors, and display muting.
  • Console control: npi::log::isPermanentConsole, npi::log::isConsoleOpen, npi::log::openConsole, and npi::log::closeConsole.

Detailed parameter, return-value, threading, and persistence behavior is documented on the corresponding declarations in Log.h.

Test: Cache Text

This test was performed to check whether the caches responsible for storing text from different parts of QMessageLogContext behave correctly.

The logging system uses three different caches:

  1. CategoryCache: Stores the log category.
  2. FileLineCache: Stores the file and line information.
  3. FunctionCache: Stores the function information.

All three caches generate text from data provided by QMessageLogContext. The context contains raw pointers to the file, function, and category texts, along with an integer line number. Each cache generates a hash from the referenced text, converts it into an index for reuse, and stores the normalized text in a pool. The test was performed to verify that the caches generate the correct indices and store the correct text.

Relevant test code:

// slot connected to a QPushButton
void MainWindow::on_logCtxCheck_btn_clicked()
{
static int counter{0};
++counter;
static std::array<char, 128> fileBuf{};
static std::array<char, 128> funcBuf{};
static std::array<char, 128> cateBuf{};
std::snprintf(fileBuf.data(), fileBuf.size(), "some/file_%d.cpp", counter);
std::snprintf(funcBuf.data(), funcBuf.size(), "void func_%d()", counter);
std::snprintf(cateBuf.data(), cateBuf.size(), "npi.temp_%d_cat", counter);
QMessageLogger(fileBuf.data(), 11, funcBuf.data(), cateBuf.data()).info()
<< QStringLiteral("Testing Context with Counter: %1").arg(counter);
}

The fileBuf, funcBuf, and cateBuf objects are static arrays, so their pointer values remain unchanged between calls to this slot. On each call, the counter is incremented and the text stored in the arrays is updated. A temporary QMessageLogger is then constructed using these pointers and a fixed line number and is used to log a string.

The same test was also performed using caches that generated their hashes from the pointer values themselves. Because the pointer values did not change between calls to the slot, the output was:

... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 1"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 2"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 3"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 4"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 5"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 6"
... npi.temp_1_cat some/file_1.cpp:11 func_1 | "Testing Context with Counter: 7"

Conclusion: The texts are stored correctly in the caches and are later retrieved by the log writer thread using their assigned indices. When pointer values are used as cache keys, the text found during the first lookup is stored and reused because the pointer addresses remain unchanged. As a result, every subsequent log incorrectly contains the first category, file, and function texts. This test demonstrates that pointer-based cache keys are unreliable because the text stored at a stable address can change. Content-derived keys correctly distinguish the updated contexts. Hashing pointer values takes approximately 70% of the time required to hash the pointed-to text. However, because pointer-based caching is not reliable, it should not be used. Content-based caching remains beneficial because previously processed file and function texts do not need to be normalized again or copied into the text pools.

Test: Text Sanitization

This test was performed to check the text sanitization. The text sanitization happens inside TextBuffer::appendChar_ function:

bool appendChar_(char chr) noexcept
{
// UTF-8 encodes non-ASCII Unicode characters using two to four bytes, all above
// 127. Since this function sanitizes one byte at a time, one Unicode character
// may therefore appear as "??", "???", or "????".
const auto uChr = static_cast<unsigned char>(chr);
if(chr == ' ' || chr == '\t' || chr == '\r' || chr == '\n' || chr == '\v' || chr == '\f') {
if(pos_ > beg_ && buf_[pos_ - 1] != ' ' && buf_[pos_ - 1] != '\n') {
if(!canAppend_(1u)) return false;
buf_[pos_++] = ' ';
}
return true;
}
if(!canAppend_(1u)) return false;
if(chr == '|') buf_[pos_++] = '/';
else if(uChr >= 32u && uChr <= 126u) buf_[pos_++] = chr;
else buf_[pos_++] = '?';
return true;
}

This means:

  • Tab, newline, etc. characters are converted to space.
  • Space is only added if:
    • previous character was not a space, and
    • current position is not the starting position.
  • The | is converted to / (since | is reserved for delimiter in log file).
  • Any character below 32, except recognized whitespace, or above 126 is replaced with ?.

Test: Logging Behavior

Fatal, Critical and Crash Handling:

Fatal and Critical logs were generated directly from MainWindow and from the stress-testing threads under extremely heavy loads.

  • All logs were written to the *.imp.log file as expected.
  • The *.imp.log file was generated only after the first fatal/critical log was generated.
  • The critical logs were also written to the normal *.log file.
  • Fatal logs resulted in immediate program termination, with a popup message and debug output, as expected.

Under heavy concurrent fatal logging, only the first fatal log displayed a popup and was written to the *.imp.log file. This behavior is expected and intentional. When multiple threads emit fatal logs concurrently, only the first thread to claim fatal ownership writes the fatal record and displays the popup. The other fatal threads wait for a fixed grace period then fail fast if the original thread hasn't done so already. This prevents competing fatal-handling paths and gives the owning thread sufficient time to write the log and display the popup. A guard is included to prevent the owning thread from waiting on itself if a re-entrant fatal log occurs on the same thread.

Limited crash-handling tests were performed. The crash handlers are installed, and crash logs are forwarded to the *.imp.log file. Some crash-handling tests could not be completed because Visual Studio intercepted the crash before the installed handlers could be invoked, for example, in the case of a stack overflow. Completing these tests would require running the executable outside Visual Studio together with all required supporting files.

Console/Debugger:

The solution was started without a debugger attached, and it correctly detected the opening and closing of the console. The display thread was started and stopped successfully multiple times during the same run.

Stuck Display Thread:

If text is selected in the console, the WriteConsoleA or WriteConsoleW function used by the display thread can become blocked and fail to return. This is one of the main reasons why console output is handled by a dedicated display thread rather than the main thread. If the display thread is blocked while the application is shutting down, the user is asked whether to abandon the display thread and continue shutting down or to continue waiting. This works as expected. Terminating the process while the display thread is blocked has no adverse side effects and is supported by design.

To perform this test, press Ctrl + F and search for text currently shown in the console. The matched text becomes selected, causing the display thread to become blocked.
